\section*{Motivation}
\addcontentsline{toc}{section}{\protect\numberline{}Motivation}

To protect business critical applications, security teams rely on a large variety of tools: \gls{sast} scanners analyze source code, \gls{sca} tools check software dependencies, \gls{dast} probes running applications, and secret scanners flag exposed credentials in code~\parencite{Chess2007, Howard2006, Stuttard2011}.

Further detection runs against build and deployment pipelines, which face their own classes of threats such as malicious dependencies published to public package registries, compromised build agents injecting code into release artifacts, tampered container base images, or leaked \gls{cicd} credentials used to push unauthorized changes~\parencite{Ohm2020, SLSA2024}. Security teams also deploy \gls{ide} plugins and security context tools integrated into \gls{ai} coding assistants such as Claude Code or GitHub Copilot to catch problems before code reaches version control~\parencite{GitHubGHAS2025, Snyk2024, Semgrep2024}.

In large enterprises, dozens of such tools produce findings through different data formats and integration patterns~\parencite{Anderson2020, Stallings2024}. As application security architect in a large organization with thousands of developers and tens of thousands of repositories, I have seen firsthand how difficult such environment is to secure. Two classes of difficulty dominate.

The first is \textbf{detection diversity}. Tools in the same category scan differently and produce different results, so a single tool is rarely sufficient~\parencite{Chess2007, McGraw2006}. Running multiple tools in parallel improves coverage but creates the opposite problem: the same vulnerability is reported several times, and findings must be deduplicated before they can be triaged or counted~\parencite{Jacobs2020, Gartner2023ASPM}.

The second is \textbf{data consolidation}. Findings lack the business context needed for prioritization: the owning application, its criticality tier, and its regulatory scope live in a separate \gls{cmdb}, not in the security tool~\parencite{AXELOS2019, Gartner2021CMDB}. Correlation within the findings themselves is nontrivial: \gls{sast} results point to a repository, file, and line, while \gls{dast} results point to a \gls{url} or host, so cross tool correlation requires additional deployment and inventory metadata~\parencite{Chess2007, Stuttard2011}. Integration patterns compound the problem. Push based models, where scanners upload reports into a vulnerability management interface, fragment data and do not scale across dozens of tools, and pull based \gls{api} connectors, where they exist, are usually gated behind commercial tiers~\parencite{DefectDojo2024, Gartner2023ASPM}.

Consolidating application security data is a data engineering problem. Industry addresses it with commercial \gls{aspm} products offering dashboards and aggregated views~\parencite{Gartner2023ASPM}, but these are proprietary products with limited customer control over internal pipelines. They can create security tool vendor lock in and constrain security teams that need to customize pipelines, apply their own \gls{ml} models, or integrate with internal systems.

The most notable open source alternative, DefectDojo, is a Django based vulnerability management web application~\parencite{DefectDojo2024}, not a data first platform. Its relational backend limits scale, and ingestion relies mostly on push based integrations or manual uploads. Pull based \gls{api} connectors exist only in the commercial DefectDojo Pro tier.

Databricks Lakewatch, announced in March 2026 and available in Private Preview at thesis submission, is a lakehouse native \gls{siem}~\parencite{Databricks2026Lakewatch}. It runs on the same lakehouse platform this thesis adopts but addresses a different domain: runtime threat detection, alert triage, and log analytics, not application security posture. The author did not have access to the Private Preview during thesis preparation, so Lakewatch is treated as related product context rather than implementation evidence. The distinction is discussed in~\autoref{sec:lakewatch}.

What is missing is a security tool vendor agnostic framework that approaches application security as a data engineering problem, providing a reusable architecture for ingestion, normalization, deduplication, and serving at enterprise scale. Vendor agnostic in this thesis means independent from individual application security tool vendors and their proprietary risk models. It does not mean that the submitted \gls{mvp} is independent from the data platform vendor: Databricks is the reference platform used to instantiate the framework, and portability to another platform is a design claim bounded in the Limitations section. The pace of tool adoption outstrips the engineering effort available to write connectors for each one. A framework that encodes integration logic declaratively, as schemas, a connector contract, and a catalog of skills an \gls{ai} coding agent can execute, \textbf{should reduce onboarding a new source to a five step procedure} (\autoref{sec:impl-methodology}) rather than a pipeline redesign, with the cost per source limited to invoking the documented skills under supervision. Step three of the procedure (use the mapping artifact as the transformation specification) is currently a specification thread, not an executed step in the \gls{mvp}, which still builds the silver DataFrame in Python. Future Work in the Conclusion records the declarative applicator as the consolidation that closes this gap. \autoref{ch:implementation} and \autoref{sec:ai-eval} examine how far this reduction holds under the empirical methodology actually exercised.

This raises the central research question: \textbf{how can diverse enterprise application security findings be consolidated into a unified, security tool vendor agnostic data model and integration framework that serves the analytical and operational needs of security teams?}

\section*{Objective}
\addcontentsline{toc}{section}{\protect\numberline{}Objective}

The main goal is to specify, design, and implement a data integration framework for enterprise application security that consolidates findings from tools into a unified platform, enabling consistent normalization, deduplication, triage, and correlation across business applications.

The subgoals are:

\begin{enumerate}
    \item \textbf{Analysis} (\autoref{ch:analysis}): Survey the application security domain and its adjacent data sources. Characterize asset inventories, software development platforms, static and dynamic security tooling, and the relevant data engineering patterns. Review related work, identify the research gap, select source systems to carry forward, and summarize the derived requirements. The \gls{api} analysis per source grounding these findings is collected on the external \href{https://vkraus.github.io/appsec-mvp/}{documentation site}.
    \item \textbf{Framework} (\autoref{ch:framework}): Use the requirements summary to propose a reusable blueprint covering solution architecture, a medallion based data model (bronze, silver, gold)~\parencite{Strengholt2025}, a connector framework, and an analytics and serving framework. The blueprint targets the Databricks lakehouse~\parencite{Lee2024, DatabricksUC2025, DatabricksLDP2025} while separating general patterns from platform specific choices. The technology rationale is given in~\autoref{sec:tech-stack}.
    \item \textbf{Implementation} (\autoref{ch:implementation}): Produce a reference implementation on Databricks that instantiates the framework for the nine selected sources. All nine ship the generated connector artifact set (configuration, ingest and transform modules, mappings, bundle resources, source runtime where applicable, and requirement bound tests). Their live source exercise and Spark wrapper completeness differ by source and are stated explicitly in \autoref{sec:impl-results} and the Limitations section of the Conclusion. The implementation also includes the platform app to repository linker and analytics/serving artifacts. The \href{https://vkraus.github.io/appsec-mvp/platform/reference/catalog/}{traceability matrix} records PASS or N/A for every (requirement~$\times$~source) cell. The deliverable is a minimum viable product on a sample chosen to cover the ingestion and integration patterns the framework must support, not an exhaustive integration of every security tool. Validation runs through automated tests with requirement traceability and \gls{ldp} data quality expectations.
\end{enumerate}

The scope is application security posture across three tiers of detection. \textbf{Static testing} covers preexecution analysis of source, dependencies, configuration, and build artifacts: \gls{sast}, \gls{sca}, secret scanning, container and \gls{iac} scanning, and supply chain integrity checks. \textbf{Dynamic testing} covers active probing of running applications: \gls{dast} (OWASP ZAP~\parencite{OWASPZAP2024}) and penetration testing. \textbf{Runtime security} covers observational telemetry from production systems. One representative source (AWS WAF sampled requests~\parencite{AWSWAF2026}) is included so the model covers runtime findings linked to applications through deployment metadata, although live WAF tenant exercise remains outside the submitted evidence. Broader runtime operations (threat detection, incident response, log analytics) are out of scope.

\autoref{ch:analysis} and \autoref{ch:framework} are framed against the full \gls{aspm} scope. \autoref{ch:implementation} instantiates the framework against the nine sources selected in \autoref{sec:selected-sources}. Onboarding a tenth source repeats the procedure described in \autoref{sec:impl-methodology} without changes to the framework.

The intended audience is application security architects and data platform engineers who need to consolidate security findings at scale without lockin to one application security tool vendor.

\section*{Methodology}
\addcontentsline{toc}{section}{\protect\numberline{}Methodology}

This thesis follows the design science research methodology of~\textcite{Hevner2004, Peffers2007} in three phases aligned with the main chapters. The \textbf{analysis} phase combines a literature review with a systematic study of source systems, identifies the research gap, and summarizes the derived requirements. The \textbf{framework} phase designs the architecture, data model, connector contract, and analytics patterns. The \textbf{implementation} phase targets a reference implementation with an \gls{ai} instantiable integration layer. In this thesis, \gls{ai} instantiable means that a human supervised coding agent can generate connector artifacts from the framework templates and pass the specified review and test cycle. A prompt based chain of four skills (analyze-source, provision-source, generate-connector, validate-implementation) was authored from the connector contract and run across all nine source specifications under reviewer subagent supervision, producing connector modules for each source and validation evidence. \autoref{sec:ai-eval} grades the outcome.

The thesis delivers three contributions: (1) a \textbf{requirements specification}, (2) a \textbf{reusable framework} covering architecture, data model, connector contract, and analytics and serving patterns, and (3) a \textbf{reference implementation} on Databricks. The integration layer is \gls{ai} instantiable in the specific sense that a human supervised coding agent can generate connector artifacts from the framework templates and pass the specified review and test cycle. \autoref{sec:ai-eval} evaluates this claim.

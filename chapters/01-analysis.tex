\chapter{Analysis}
\label{ch:analysis}

This chapter surveys the literature and analyzes the functional domains relevant to building an application security data platform. Each section covers one domain, combining theoretical foundations with practical tool and \gls{api} analysis. The focus is on reviewing existing knowledge, observing source system interfaces, data models, and integration patterns, not on prescribing a solution. Technology choices for the target platform are deferred to \autoref{ch:framework} and \autoref{ch:implementation}.

\autoref{sec:app-inventory} establishes the business and infrastructure asset context underlying all security findings. \autoref{sec:sw-dev-analysis} examines software development platforms as data sources. Application security tooling is split into two sections: \autoref{sec:static-appsec} covers tools that analyze source code and build artifacts before deployment, while \autoref{sec:dynamic-appsec} covers tools that test running applications and monitor deployed infrastructure. This separation reflects a fundamental difference in how findings are produced and correlated: static tools identify targets by repository and file path, while dynamic tools identify targets by \gls{url}, host, or cloud resource, requiring different integration strategies. \autoref{sec:data-eng-analysis} covers the data engineering patterns that underpin the framework's design. Finally, \autoref{sec:related-work} surveys existing solutions and identifies the gap this thesis addresses.

\section{Asset Discovery and Inventory}
\label{sec:app-inventory}

Asset discovery and inventory is the foundational data source for any application security data platform. It establishes the business context for all security findings. On the business side, organizations maintain application inventories in a \gls{cmdb} or a custom-built catalog. On the infrastructure side, cloud providers and container orchestrators expose asset inventories through \glspl{api}. Without a reliable catalog of business applications and their mapping to technical and infrastructure assets, a vulnerability discovered in a repository or a running service cannot be attributed to an owner, assessed for business impact, or prioritized against organizational risk criteria.

%%% 1.1.1 %%%

\subsection{Application Portfolio Management}

Enterprise organizations maintain catalogs of their business applications with metadata such as application name, description, ownership information, lifecycle status, and relationships to other assets~\cite{AXELOS2019}.

These registries also capture security-relevant attributes. Information security is commonly assessed along three dimensions known as the \gls{cia} triad: confidentiality (preventing unauthorized disclosure), integrity (preventing unauthorized modification), and availability (ensuring authorized access)~\cite{Stallings2024}. Business impact assessments evaluate all three \gls{cia} dimensions to produce criticality ratings, commonly structured as tiers: Tier~1 for mission-critical applications, Tier~2 for important supporting systems, and Tier~3 for non-critical internal tools. Separately, regulatory scope flags identify which compliance frameworks apply to a given application, further contributing to the security requirement set.

The most important attribute from a data integration perspective is the mapping between business applications and their technical assets. A single business application may span multiple source code repositories, microservices, infrastructure components, and deployment environments. This mapping serves as the glue connecting technical security findings to business context. When the framework ingests a vulnerability from a \gls{sast} scanner linked to a specific repository, the application inventory mapping determines which business application is affected, who owns it, and how critical it is. This enables the risk-aware prioritization that stakeholders require.

%%% 1.1.2 %%%

\subsection{Configuration Management Databases}

The most common \gls{cmdb} platform in enterprise environments is ServiceNow, holding over 44\% of the global \gls{itsm} market share~\cite{Gartner2024ITSM}. It serves as the reference platform for this thesis. A \gls{cmdb} organizes all managed assets as \glspl{ci}, each with attributes describing its type, status, and ownership~\cite{AXELOS2019}.

ServiceNow arranges \glspl{ci} in a class hierarchy rooted at the \texttt{cmdb\_ci} base table. Each subclass inherits base attributes (name, \texttt{sys\_id}, operational status, environment) and adds domain-specific fields. For application inventory purposes, the most relevant class is \texttt{cmdb\_ci\_appl} (Application), which extends the base \gls{ci} with attributes such as version, business unit, used-for classification, and references to the owning support group~\cite{ServiceNowCMDB2024}.

Beyond the application record itself, the \gls{cmdb} captures relationships between \glspl{ci} through a dedicated relationship table (\texttt{cmdb\_rel\_ci}). These relationships model dependencies such as ``runs on'' (application to server), ``depends on'' (application to database), and ``hosted on'' (application to cloud service). For the framework, the most valuable relationships are those linking business applications to technical assets that correspond to entities in the security data: repository names, deployment targets, and infrastructure components. ServiceNow also allows organizations to define custom attributes and relationship types, so the specific fields available for ingestion may vary between deployments.

%%% 1.1.3 %%%

\subsection{Integration Options}

Integrating \gls{cmdb} data into an external data platform requires choosing between two strategies: pulling data from ServiceNow via its \glspl{api}, or pushing data from a custom ServiceNow application to an external target.

\subsubsection{ServiceNow APIs}

ServiceNow exposes two complementary \gls{rest} \glspl{api} for \gls{cmdb} data extraction. The Table \gls{api} provides generic CRUD operations against any ServiceNow table through the endpoint \texttt{/api/now/table/\{tableName\}}~\cite{ServiceNowTableAPI2024}. Responses are \gls{json}-formatted, with support for server-side filtering (\texttt{sysparm\_query}), field selection (\texttt{sysparm\_fields}), and pagination via \texttt{sysparm\_limit} and \texttt{sysparm\_offset} (default maximum of 10\,000~records per request). The \texttt{sysparm\_display\_value} parameter resolves reference fields to human-readable names instead of internal \texttt{sys\_id} values.

The \gls{cmdb} Instance \gls{api} (\texttt{/now/cmdb/instance/\{className\}}) provides a \gls{cmdb}-aware alternative that understands the \gls{ci} class hierarchy~\cite{ServiceNowCMDB2024}. It can retrieve a \gls{ci} with its relationships in a single call, reducing the number of \gls{api} calls needed to reconstruct the application-to-asset mapping. However, it is more constrained in its query capabilities than the Table \gls{api}.

Both \glspl{api} require authentication, typically through Basic Authentication with a service account granted the \texttt{rest\_service} or \texttt{cmdb\_read} role, or through OAuth~2.0 for more security-conscious deployments. Rate limits vary by instance configuration and are governed by platform transaction quotas rather than per-endpoint limits. For incremental data extraction, the \texttt{sys\_updated\_on} timestamp field present on all records serves as a reliable high-water mark, allowing consumers to query only records modified since the last extraction.

Any pull-based integration must handle authentication, pagination, rate limiting, and incremental state management. Several integration libraries and platform-native connectors abstract these concerns; the specific tooling choice depends on the target data platform and is discussed in \autoref{sec:servicenow-impl}.

\subsubsection{ServiceNow Application}

An alternative to pulling data is to push it from the source. ServiceNow supports building scoped applications that run on the platform itself. A custom application can use Outbound REST Messages to send \gls{cmdb} data to an external target (e.g., a cloud storage bucket or a \gls{rest} endpoint) on a schedule defined through Scheduled Jobs or Flow Designer. The application can also expose a Scripted \gls{rest} \gls{api}~\cite{ServiceNowScriptedREST2024}, a custom endpoint that shapes the data exactly as the consumer needs it, pre-joining application records with their relationships and custom attributes in a single response.

The advantage is full access to ServiceNow's internal scripting capabilities, relationship traversal, and business logic without external \gls{api} call overhead. The disadvantage is that development and maintenance happen inside the ServiceNow platform, requiring ServiceNow development expertise and a separate deployment lifecycle. Changes to the \gls{cmdb} schema or extraction logic must be coordinated across two platforms. This approach is best suited for organizations with mature ServiceNow development teams that prefer to own the data export logic on the source side.

\subsubsection{Integration Challenges}

In implementation phase, the application inventory presents the most significant integration challenge among all data sources because it is the least standardized. Security testing tools converge around common \gls{api} patterns and output formats, but each organization structures its application inventory differently: the hierarchy of applications, the granularity of asset mapping, and the attributes captured vary substantially~\cite{AXELOS2019}. This makes the application inventory connector the hardest to generalize and the one most likely to require implementation-specific customization.

Data quality in \glspl{cmdb} is a persistent concern~\cite{Gartner2021CMDB}. Application records may be incomplete (missing ownership or criticality assignments), outdated (reflecting decommissioned applications still listed as active), or inconsistently maintained across business units. Any integration must account for these quality issues through validation rules and default values that surface problems without blocking the data pipeline.

Despite these difficulties, the application inventory is indispensable. Without the business context it provides, security findings lack the organizational meaning needed for effective prioritization and governance.

%%% 1.1.4 %%%

\subsection{Cloud Asset Discovery}
\label{sec:cloud-asset-discovery}

Major cloud providers offer asset inventory \glspl{api}. \gls{aws} Config maintains a continuously updated resource inventory through a \gls{rest} \gls{api}. Azure Resource Graph supports a query language for cross-subscription metadata retrieval. Google Cloud provides the Cloud Asset Inventory \gls{api}. All three offer mature \glspl{sdk} that abstract authentication, pagination, and retry logic. Kubernetes exposes workload metadata (deployments, pods, container specifications) through its \gls{api}, enabling the framework to trace from runtime workloads to container images and, through \gls{cicd} metadata, to source repositories.

Cloud asset data serves as the infrastructure counterpart to the business application inventory in the preceding subsections. While the application inventory maps business applications to repositories and teams, cloud asset discovery maps applications to their runtime infrastructure: compute instances, containers, load balancers, and network configurations. Joining these two inventories enables the framework to link security findings from any layer to both code owners and infrastructure owners.

%%% 1.1.5 %%%

\subsection{Cross-Layer Correlation}
\label{sec:runtime-correlation}

The central challenge in asset inventory is correlating identifiers across layers. Security tools that analyze source code identify targets by repository, file path, and code location. Tools that operate on running infrastructure identify targets by host, container, cloud resource, or \gls{url}. Bridging these two coordinate systems requires the application-to-asset mapping described in the preceding subsections, which serves as the joining entity linking runtime infrastructure to business applications and their source repositories.

This correlation enables cross-layer analyses: tracing a runtime vulnerability to the code that introduced it, linking a \gls{waf} alert to the responsible application and team, or determining which \gls{iac} finding corresponds to a live \gls{cspm} detection. Without it, findings from dynamic security tools (\autoref{sec:dynamic-appsec}) remain isolated from the development context, limiting their actionability. The data model in \autoref{ch:framework} addresses this by defining explicit relationships between application entities, infrastructure assets, and security findings across all layers.

\section{Software Development}
\label{sec:sw-dev-analysis}

Modern software is built collaboratively from source code, organized in repositories, and deployed through automated pipelines~\cite{Sommerville2015, Pressman2019}. While \autoref{sec:app-inventory} established the business context for security findings, the platforms that support software development provide the technical entities around which those findings are organized. Repositories, build pipelines, and issue trackers form the second major data source category for the framework.

These platforms share common integration patterns that simplify connector design. All expose \gls{rest} \glspl{api} with \gls{json} responses as the primary integration surface. Authentication relies on token-based mechanisms: OAuth tokens, \glspl{pat}, or service account credentials. Pagination follows either offset-based or cursor-based patterns, and all platforms impose rate limits that consumers must handle through backoff strategies. This consistency enables shared connector logic for authentication, pagination, rate limiting, and error recovery across tools.

%%% 1.2.1 %%%

\subsection{Source Code Management}

\textcite{Chacon2014} provide a thorough treatment of Git, covering branching strategies, merging, and distributed workflows, while \textcite{Skoulikari2024} offers a more recent visual introduction. \textcite{Winters2020} extend this perspective to organizational scale, describing how large engineering teams manage repositories with thousands of contributors. For this thesis, the repository is the primary entity around which security findings are grouped, as detailed in the data model in \autoref{ch:framework}.

Development teams host their Git repositories on cloud-based \gls{scm} platforms. GitHub is the dominant platform, with over 150 million developers and adoption by 92\% of Fortune~100 companies~\cite{GitHub2025Octoverse}. The 2025 Stack Overflow Developer Survey reports GitHub at 81\% adoption for code collaboration, followed by GitLab at 36\%~\cite{StackOverflow2025}. Bitbucket and Azure DevOps serve smaller but significant enterprise segments. Most large organizations use more than one platform, whether through acquisitions, team preferences, or regulatory separation, making multi-platform ingestion a practical requirement.

Beyond source code, \gls{scm} platforms expose metadata relevant to security governance. Repository attributes include the primary programming language, creation and last activity dates, visibility settings (public or private), and archive status. Branch protection rules indicate the maturity of the development process. Team and contributor assignments establish ownership relationships that feed into the application-to-team mapping described in \autoref{sec:app-inventory}.

These platforms share common \gls{api} patterns. GitHub exposes two complementary \glspl{api}~\cite{GitHubAPI2024}: a \gls{rest} \gls{api} (v3) with resource-oriented endpoints and page-based pagination, and a GraphQL \gls{api} (v4) that enables selective field retrieval with cursor-based pagination. Both use the same authentication mechanisms (OAuth tokens or \glspl{pat}) and share a rate limit of 5\,000 requests per hour. GitLab offers a similar dual \gls{rest}/GraphQL surface~\cite{GitLabAPI2024}. Azure DevOps provides a \gls{rest} \gls{api} authenticated through Azure Active Directory, with comparable response formats and pagination. Across all platforms, authentication is token-based and responses are \gls{json}-formatted, enabling shared connector logic for authentication, pagination, and rate limit handling.

%%% 1.2.2 %%%

\subsection{Continuous Integration and Delivery}

\Gls{sdlc} practices have shifted from sequential models to iterative methodologies and DevOps. \textcite{Forsgren2018} present empirical evidence that high-performing teams deploy more frequently with shorter lead times, achieved through \gls{cicd} automation. \textcite{Kim2021} complement this with practical guidance for implementing DevOps pipelines at scale. The \gls{cicd} pipeline, an automated sequence of build, test, and deploy stages, is relevant to this thesis because each stage can integrate security tools whose findings the framework consolidates.

GitHub Actions is the most widely adopted \gls{cicd} platform, used by 62\% of developers for personal projects and 41\% in organizational settings~\cite{JetBrains2025CICD}. Jenkins remains prevalent in enterprises at 28\% organizational adoption, followed by GitLab CI at 19\%. Notably, 32\% of organizations use two or more \gls{cicd} tools, and 9\% use at least three, reinforcing the multi-platform integration challenge observed for \gls{scm} platforms.

\Gls{cicd} platforms provide contextual data about when and how security scans run. Pipeline definitions reveal which security tools are integrated into the build process. Build results indicate whether security gates passed or failed. Execution metadata records which commit was scanned, when the scan ran, and how long it took. This information serves as operational context rather than a primary finding source: knowing that a repository's last security scan ran three months ago, or that a scan consistently fails, signals coverage gaps and tool health that complement the findings from security tools.

Integration patterns vary more across \gls{cicd} platforms than across \gls{scm} tools. GitHub Actions exposes build data through its \gls{rest} \gls{api} with \gls{json} responses, consistent with the broader GitHub \gls{api} surface. Jenkins uses an \gls{xml}-based \gls{api} with a different authentication model. Azure Pipelines follows the Azure DevOps \gls{rest} conventions. Despite these differences, the retrieved data is structurally similar: pipeline identifiers, run statuses, timestamps, and associated commit references.

%%% 1.2.3 %%%

\subsection{Issue Tracking}

Issue tracking systems are relevant to the framework because they track remediation status. When a security finding is assigned for remediation, an issue is typically created in the team's tracker, either manually or through automation. The framework must read issue status to determine whether a finding is under active remediation, who is responsible, and whether it has been resolved within the required \gls{sla} window.

Jira is the dominant issue tracking platform in enterprise environments. The 2025 Stack Overflow Developer Survey reports Jira at 46\% adoption, behind only GitHub (81\%) and ahead of GitLab (36\%) for code documentation and collaboration tools~\cite{StackOverflow2025}. Azure DevOps Work Items serves organizations within the Microsoft ecosystem. GitHub Issues and GitLab Issues provide lightweight built-in tracking tightly coupled with their respective \gls{scm} platforms. As with \gls{scm} and \gls{cicd} tools, many organizations use multiple trackers across different teams.

These platforms expose \gls{rest} \glspl{api} with \gls{json} responses and paginated results. Jira provides \gls{jql}, a query language for precise filtering by project, status, labels, or custom fields, enabling retrieval of only security-relevant issues without downloading entire project backlogs. GitHub and GitLab expose issues through the same \gls{api} surfaces used for repository data. Most trackers also support webhooks for real-time event notifications when issue status changes, reducing reliance on periodic polling.

The integration with issue trackers is bidirectional. The framework reads remediation status and may also create new issues when findings require attention. This bidirectional flow introduces complexity around idempotency (avoiding duplicate issue creation) and state synchronization (keeping the framework's view consistent with the tracker's current state).

\section{Static Application Security}
\label{sec:static-appsec}

Application security encompasses the practices and tools for identifying vulnerabilities in software throughout its lifecycle~\cite{Anderson2020, Stallings2024}. \textcite{McGraw2006} advocated for security touchpoints spanning the entire development process. The DevSecOps paradigm~\cite{Mack2023, Kim2021} realizes this vision by embedding security testing into \gls{cicd} pipelines. \Gls{sast} examines source code, \gls{sca} checks third-party dependencies, secret scanners flag leaked credentials, and \gls{dast} probes running applications. The practical consequence is a high volume of security data from tools with different \glspl{api}, output formats, and severity models. The \gls{owasp} Top~10 classifies common web application risks~\cite{OWASP2021}, but it does not define a data interchange standard.

Several cross-cutting data standards bring partial consistency. The \gls{cve} system assigns unique identifiers to known vulnerabilities~\cite{MITRE2024}. \Gls{cwe} classifies underlying weakness types~\cite{CWE2024}. \Gls{cvss} scores attack vector, complexity, and impact on a 0--10 scale~\cite{FIRST2019}. \Gls{epss} complements \gls{cvss} with a predictive signal~\cite{Jacobs2021}: the probability that a vulnerability will be exploited within 30~days, computed by \gls{ml} models. \Gls{cisa} maintains the \gls{kev} catalog~\cite{CISAKEV2024}. It adds a third signal: confirmed active exploitation from real-world incident data. Together, \gls{cvss}, \gls{epss}, and \gls{kev} form a three-signal enrichment model used throughout the framework.

For data interchange, \gls{sarif} defines a \gls{json}-based format for static analysis results~\cite{OASIS2024}. CycloneDX and \gls{spdx} provide \gls{sbom} schemas~\cite{CycloneDX2024, SPDX2024}. \Gls{ocsf} standardizes security event exchange~\cite{OCSF2024}. It targets \gls{siem} and \gls{soar} use cases. No single format covers all tool categories. \Gls{sarif} addresses static analysis but not \gls{sca} or runtime findings. CycloneDX and \gls{spdx} cover software composition, not code-level vulnerabilities. \Gls{ocsf} serves security operations, not application security posture. This gap motivates the normalization model in \autoref{ch:framework}.

The analysis of security tooling is organized into two sections by operational model. This section covers static analysis tools that examine source code and build artifacts without executing the application. Their findings reference repositories, file paths, and line numbers, making them directly attributable to development teams. \autoref{sec:dynamic-appsec} covers tools that operate on running applications and deployed infrastructure, where findings reference \glspl{url}, hosts, and cloud resources, requiring additional mapping to connect them back to source code. Mobile application security testing is excluded from this analysis, as the framework targets web applications and backend services.

%%% 1.3.1 %%%

\subsection{Static Application Security Testing}
\label{sec:code-security}

\Gls{sast} examines source code, bytecode, or binary code for vulnerabilities without executing the program. \textcite{Chess2007} provide the foundations, covering taint analysis, control flow analysis, and pattern matching to detect injection flaws, buffer overflows, and insecure data handling. A key tradeoff is between detection coverage and false positive rates: tools with broader rule sets catch more issues but generate more noise~\cite{Chess2007}.

SonarQube provides the most mature integration surface among \gls{sast} tools. Its \gls{rest} \gls{api} offers paginated endpoints with server-side filtering by project, severity, status, and rule, returning \gls{json} responses~\cite{SonarQube2024}. Beyond individual findings, the \gls{api} exposes project-level quality metrics useful for coverage analysis. Semgrep operates as a \gls{cli} tool running user-defined rules against source code, producing \gls{json} or \gls{sarif} output~\cite{Semgrep2024}. The Semgrep Cloud Platform adds a centralized \gls{api} for managing rules and results across projects. Checkmarx exposes a \gls{rest} \gls{api} for scan management and result retrieval, with \gls{sarif} export support.

\gls{scm} platforms also provide built-in \gls{sast} capabilities. GitHub Code Scanning runs CodeQL analysis and exposes results through the code scanning alerts \gls{api}~\cite{GitHubAPI2024}. GitLab integrates \gls{sast} as a \gls{cicd} pipeline job with findings accessible through its security \gls{api}~\cite{GitLabAPI2024}. When both platform-native and standalone tools scan the same repository, the resulting overlap requires deduplication in the normalization layer.

Each finding typically includes a rule identifier, the affected file path and line number, a severity rating, the offending code snippet, and remediation guidance. However, severity models differ across tools. SonarQube uses a five-level scale (blocker, critical, major, minor, info). Semgrep and Checkmarx use high, medium, and low, sometimes with a numerical score. This divergence makes severity normalization one of the most important tasks in the framework's transformation layer. The reference implementation integrates SonarQube, Semgrep, and additional \gls{sast} sources as described in \autoref{ch:implementation}.

%%% 1.3.2 %%%

\subsection{Software Composition Analysis}
\label{sec:supply-chain-security}

\Gls{sca} identifies known vulnerabilities in third-party dependencies. Modern applications commonly include hundreds of transitive dependencies, creating a large attack surface~\cite{Anderson2020}. \textcite{Ohm2020} provide a systematic review of supply chain attacks, including typosquatting, dependency confusion, and malicious package injection. \gls{sca} tools analyze dependency manifests, resolve the full dependency tree, and cross-reference versions against vulnerability databases such as the \gls{nvd}.

Snyk provides \gls{rest} \glspl{api} (legacy v1 and current v3) returning \gls{json} responses with filtering by severity and project~\cite{Snyk2024}. Dependabot, integrated into GitHub, exposes alerts through the GitHub GraphQL \gls{api}~\cite{GitHubAPI2024}. \gls{owasp} Dependency-Track is an open-source platform that ingests \glspl{sbom} in CycloneDX or \gls{spdx} format and identifies vulnerabilities against multiple databases~\cite{DependencyTrack2024}. It provides a \gls{rest} \gls{api} for project management and findings retrieval. Many \gls{sca} tools also generate \glspl{sbom}~\cite{CycloneDX2024, SPDX2024}, increasingly required by regulatory frameworks~\cite{NTIA2021}. The reference implementation integrates Dependabot, Dependency-Track, and GitLab dependency scanning, as described in \autoref{ch:implementation}.

\gls{sca} output is comparatively well standardized because the underlying data originates from shared public databases. Each finding typically includes the vulnerable dependency name and version, a \gls{cve} identifier, a \gls{cvss} score, the fixed version when available, and exploitability metadata. Despite this, transitive dependency resolution remains a challenge: different tools may resolve the same dependency tree differently, causing one tool to flag a \gls{cve} while another does not. The framework must handle this during deduplication, recognizing that the same \gls{cve} reported by multiple tools against the same repository likely represents a single issue.

\gls{sca} tools also detect license violations (e.g., GPL-licensed code in proprietary applications), producing compliance findings alongside vulnerability data. The \gls{slsa} framework~\cite{SLSA2024} complements \gls{sca} from a different angle: while \gls{sca} checks whether dependencies contain known vulnerabilities, \gls{slsa} verifies the integrity and provenance of build artifacts, ensuring they have not been tampered with during the build process. Both concerns feed into the broader supply chain security picture.

\subsection{Secret Detection}
\label{sec:lifecycle-security}

Secret detection tools scan version control history for credentials, \gls{api} keys, tokens, and other sensitive material. Once a secret is committed, it persists in Git history even after deletion from the working tree. Tools use two complementary detection approaches. Pattern-based detection matches strings against known credential formats using regular expressions. Entropy-based detection flags strings with unusually high randomness, catching novel credential formats at the cost of higher false positive rates.

GitLeaks scans repositories against over 150 predefined patterns and produces \gls{json} output~\cite{Gitleaks2024}. It runs as a \gls{cli} tool, typically in \gls{cicd} pipelines or pre-commit hooks. TruffleHog supports over 800 secret types, combines pattern and entropy analysis, and adds live credential verification to confirm whether a detected secret remains valid~\cite{TruffleHog2024}. Both tools operate as \gls{cli} tools without server-side \glspl{api}; integration requires executing the tool and parsing its output.

Platform-integrated scanners take a different approach. GitHub Secret Scanning exposes alerts through the GitHub \gls{rest} \gls{api} with webhook notifications for new detections~\cite{GitHubAPI2024}. GitLab Secret Detection runs as a \gls{cicd} pipeline job and reports results through GitLab's security dashboard and \gls{api}~\cite{GitLabAPI2024}. These tools are simpler to integrate because they use existing platform \gls{api} surfaces, but they only cover repositories hosted on their respective platforms.

The primary integration challenge is the absence of a standard output format. Each tool defines its own \gls{json} schema, and none supports \gls{sarif}. Findings include the secret type, file path, commit reference, and sometimes a validity status, but field names and structures vary across tools.

%%% 1.3.4 %%%

\subsection{Container Image Scanning}
\label{sec:container-security}

Container image scanning examines built container images for vulnerabilities in \gls{os} packages, application libraries, and configuration. While \gls{sca} analyzes source-level dependency manifests, container scanners operate on assembled images, detecting \gls{os}-level vulnerabilities and misconfigurations that source-level analysis does not cover.

Trivy is a widely adopted open-source scanner supporting container images, filesystems, and Git repositories~\cite{Trivy2024}. It produces \gls{json} or \gls{sarif} output and integrates into \gls{cicd} pipelines as a \gls{cli} tool. Commercial alternatives such as Aqua and Prisma Cloud add registry scanning, policy enforcement, and centralized management through \gls{rest} \glspl{api}. Findings typically include the vulnerable package name and version, a \gls{cve} identifier, the fixed version, and the image layer where the package was introduced.

The integration challenge is linking image vulnerabilities to source code repositories. Container images are identified by registry, name, and tag, not by the source code that produced them. Establishing this mapping requires tracing through \gls{cicd} metadata: which pipeline built the image, from which repository, at which commit.

%%% 1.3.5 %%%

\subsection{Infrastructure as Code Security}
\label{sec:iac-security}

\Gls{iac} security tools perform static analysis on infrastructure definitions: Terraform configurations, CloudFormation templates, Kubernetes manifests, and Dockerfiles. They detect misconfigurations before deployment, such as overly permissive access policies, unencrypted storage, exposed ports, and missing logging.

Checkov is a prominent open-source scanner supporting over 1\,000 built-in policies across multiple \gls{iac} frameworks~\cite{Checkov2024}. tfsec focuses on Terraform, and KICS covers a broad range of formats. All operate as \gls{cli} tools producing \gls{json} or \gls{sarif} output. Findings are file-and-line-based, structurally similar to \gls{sast} output, but target infrastructure configuration rather than application logic.

Kubernetes admission controllers such as OPA/Gatekeeper and Kyverno enforce policies at deploy time, rejecting workloads that violate security constraints. They occupy a middle ground between pre-deployment \gls{iac} scanning and post-deployment \gls{cspm}: the policies are defined as code, but enforcement happens at the cluster boundary. Their violation logs provide an additional signal about infrastructure security posture.

These tools complement the runtime monitoring tools discussed in \autoref{sec:dynamic-appsec}. \gls{cspm} scanners and \gls{vmdr} platforms detect the same misconfiguration classes after deployment in the live environment. Correlating pre-deployment \gls{iac} findings with post-deployment runtime detections is a challenge the framework addresses through its unified data model.

\section{Dynamic Application Security}
\label{sec:dynamic-appsec}

While the static analysis tools in \autoref{sec:static-appsec} examine source code and build artifacts, the tools in this section operate on running applications and deployed infrastructure. The cross-cutting data standards introduced in \autoref{sec:static-appsec}, particularly \gls{cve}, \gls{cvss}, \gls{epss}, and \gls{kev}, apply equally to dynamic findings. The cross-layer correlation challenge that connects these findings to business applications is addressed in \autoref{sec:runtime-correlation}.

%%% 1.4.1 %%%

\subsection{Dynamic Application Security Testing}
\label{sec:dast}

\Gls{dast} tests running applications by sending crafted \gls{http} requests and analyzing responses for vulnerability indicators~\cite{Stuttard2011}. Unlike \gls{sast}, which works on source code, \gls{dast} requires a deployed application and detects vulnerabilities that manifest only at runtime, such as authentication bypass, server misconfiguration, and certain injection flaws.

\gls{owasp} \gls{zap} is the most widely used open-source \gls{dast} tool, providing a \gls{rest} \gls{api} for scan management and result retrieval with \gls{json} and \gls{xml} output~\cite{OWASPZAP2024}. Burp Suite exposes a \gls{rest} \gls{api} in its Enterprise edition; the Professional edition is a desktop tool without programmatic access. Findings from both tools include the target \gls{url}, the affected \gls{http} parameter, the vulnerability type mapped to \gls{cwe} identifiers~\cite{CWE2024}, exploitation evidence, and a confidence rating.

The core integration challenge is that \gls{dast} findings are \gls{url}-based, not code-based. A \gls{sast} finding points to a file and line in a repository; a \gls{dast} finding points to a \gls{url} endpoint. Mapping \gls{url}-based findings to source repositories requires deployment metadata or application inventory data from \autoref{sec:app-inventory}. Without this mapping, \gls{dast} findings can be attributed to applications but not to development teams or code locations.

%%% 1.4.2 %%%

\subsection{Penetration Testing}
\label{sec:penetration-testing}

Manual penetration testing traditionally produces no machine-readable output. External firms deliver results as narrative \gls{pdf} or Word reports, requiring a structured upload mechanism (e.g., a \gls{json} or \gls{csv} template) for security teams to transcribe key fields. \gls{ml}-based document parsing could automate extraction, though the inconsistent formatting of penetration test reports makes this non-trivial.

Emerging platforms such as XBOW use autonomous \gls{ai} agents to perform penetration testing at scale, delivering validated findings with reproducible exploit evidence~\cite{XBOW2024}. These platforms offer \gls{api} access for test orchestration and integrate with security data ecosystems, moving penetration testing toward the structured, automatable data exchange that other tool categories already provide.

Despite low frequency, penetration testing findings are often among the most critical, representing validated exploitable vulnerabilities. The framework must accommodate both manual uploads and automated \gls{api} ingestion to cover the full spectrum of penetration testing practices.

%%% 1.4.3 %%%

\subsection{Web Application Firewalls}
\label{sec:waf}

\Glspl{waf} operate at the network perimeter, inspecting inbound \gls{http} traffic against rule sets such as the \gls{owasp} Core Rule Set. They log blocked and flagged requests, recording the matched rule, request details, and action taken. Most commercial \glspl{waf} (\gls{aws} WAF, Cloudflare, Akamai) expose \gls{rest} \glspl{api} for log retrieval and configuration management.

These platforms typically bundle \gls{ddos} protection alongside \gls{waf} capabilities. \gls{ddos} mitigation services filter volumetric and application-layer attacks, logging traffic patterns, attack signatures, and mitigation actions. This telemetry provides availability impact data that complements the vulnerability-focused findings from other tool categories.

\Glspl{waf} and \gls{ddos} protection generate high-volume event data rather than discrete findings. The framework ingests aggregated attack patterns and anomaly indicators rather than individual request logs, focusing on the subset relevant to application security posture assessment.

%%% 1.4.4 %%%

\subsection{Runtime Application Self-Protection}
\label{sec:rasp}

\Gls{rasp} tools instrument the application runtime, detecting attacks such as \gls{sql} injection and path traversal from within the application context. Unlike \glspl{waf}, which operate at the network perimeter, \gls{rasp} can correlate attacks with specific application functions and code paths. This produces richer contextual data per event, but \gls{rasp} adoption remains limited compared to \glspl{waf}, and integration surfaces vary across vendors.

Like \glspl{waf}, \gls{rasp} tools produce event streams rather than discrete findings. The integration approach is similar: the framework consumes aggregated indicators rather than raw event logs.

%%% 1.4.5 %%%

\subsection{Runtime API Security}
\label{sec:api-security}

Traditional \gls{dast} tools actively probe applications with crafted requests. Runtime \gls{api} security platforms take a different approach: they passively monitor live \gls{api} traffic, build behavioral baselines, and detect anomalies that indicate abuse~\cite{OWASPAPI2023}. This continuous monitoring catches threats that active scanning misses, including business logic abuse, account takeover patterns, and data exfiltration through legitimate \gls{api} endpoints.

Salt Security pioneered this category, applying \gls{ai}-based behavioral analysis to \gls{api} traffic to discover shadow \glspl{api}, detect anomalies, and identify attack patterns~\cite{SaltSecurity2024}. Noname Security, acquired by Akamai in 2024~\cite{AkamaiAPISecurityZD2024}, offers similar capabilities: \gls{api} discovery, vulnerability detection, and runtime protection integrated into Akamai's edge platform. Both expose \gls{rest} \glspl{api} for configuration and findings retrieval.

Runtime \gls{api} security produces event-oriented data similar to \glspl{waf} and \gls{rasp}, but with richer \gls{api}-specific context: the affected endpoint, request/response patterns, the deviation from baseline behavior, and the attack classification. The framework treats these as a continuous finding source, ingesting aggregated indicators rather than raw traffic data.

%%% 1.4.6 %%%

\subsection{Vulnerability Management and Cloud Posture}
\label{sec:vmdr-cspm}

\Gls{vmdr} tools scan infrastructure for \gls{os} vulnerabilities, missing patches, and exposed services. Qualys exposes data through a \gls{rest} \gls{api} with \gls{xml} responses. Wiz uses a GraphQL \gls{api} for selective queries across cloud environments. These tools produce findings tied to infrastructure identifiers (hostnames, IP addresses, cloud resource \glspl{arn}), not to source code locations.

\Gls{cspm} tools complement \gls{vmdr} by evaluating cloud configurations against compliance benchmarks such as \gls{cis} Benchmarks and organizational policies. Findings indicate misconfigurations (public S3 buckets, overly permissive \gls{iam} roles, unencrypted storage) rather than software vulnerabilities. \Gls{cspm} overlaps with \gls{iac} security (\autoref{sec:iac-security}): both detect the same misconfiguration classes, but \gls{iac} tools scan before deployment while \gls{cspm} scans the live environment. Correlating pre-deployment and post-deployment findings is a key integration challenge.

\section{Data Engineering}
\label{sec:data-eng-analysis}

The preceding sections analyzed the sources of application security data: asset inventories, development platforms, and security testing tools across static and dynamic categories. Consolidating these heterogeneous sources into a unified analytical platform is fundamentally a data integration problem. This section surveys the architectural paradigms and engineering patterns relevant to solving it, independent of any specific platform.

%%% 1.5.1 %%%

\subsection{Data Platform Architecture}
\label{sec:data-architecture}

The literature documents a progression from data warehouses through data lakes to the lakehouse paradigm. \textcite{DAMA2017} provide a comprehensive body of knowledge for data management, establishing the vocabulary and principles referenced throughout this section. \textcite{Codd1970} established the relational model as the theoretical foundation. The data warehouse, formalized by \textcite{Inmon2005}, stores subject-oriented, integrated data for analytical decision-making using a top-down normalized approach. \textcite{Kimball2013} take a complementary bottom-up path with dimensional modeling: star schemas that organize data into fact and dimension tables optimized for queries. Both approaches assume structured sources with stable schemas, a condition that does not hold for heterogeneous security tool output.

The data lake~\cite{Miloslavskaya2016} stores raw data in its native format, deferring schema definition to consumption time (schema-on-read). This accommodates format diversity but introduces governance challenges. Without proper management, data lakes risk becoming ``data swamps'' where data is abundant but unusable~\cite{DAMA2017}.

The lakehouse architecture~\cite{Armbrust2021} combines data lake flexibility with warehouse governance by introducing open table formats that add \gls{acid} transactions, schema enforcement, and time travel on top of lake storage~\cite{Lee2024, Thalpati2024}. The lakehouse paradigm suits the application security problem: it accommodates diverse, semi-structured tool output while providing the governance and query performance required for both analytical dashboards and operational lookups.

The medallion architecture~\cite{Strengholt2025} organizes lakehouse data into three layers:
\begin{itemize}
    \item \textbf{Bronze}: Raw data with minimal transformation, preserving original source schemas.
    \item \textbf{Silver}: Cleaned, validated, and normalized data conforming to a unified schema.
    \item \textbf{Gold}: Consumption-ready aggregated metrics and enriched datasets.
\end{itemize}
This layered approach maps naturally to the security data integration problem. The bronze layer captures raw tool output in source-native schemas. The silver layer normalizes findings across tools into a vendor-agnostic model. The gold layer computes the aggregated risk metrics and enriched datasets that stakeholders consume.

A security data platform must serve two distinct access patterns. \Gls{olap} queries power dashboards and trend analysis, operating over large aggregated datasets where query throughput matters more than write latency. \Gls{oltp} access supports operational workflows such as issue tracker integration and real-time risk lookups, where low-latency reads and writes to individual records are essential. The framework must accommodate both, a requirement that influences the serving architecture designed in \autoref{ch:framework}.

%%% 1.5.2 %%%

\subsection{Data Integration Patterns}
\label{sec:data-integration-patterns}

\textcite{Reis2022} cover data engineering fundamentals, including the distinction between \gls{etl} and \gls{elt} paradigms. \Gls{etl} transforms data before loading, requiring upfront schema knowledge and a dedicated transformation layer between source and target. \Gls{elt} loads raw data first and transforms it in place, aligning well with lakehouse architectures where distributed compute engines perform transformations at scale~\cite{Thalpati2024}. For security data integration, \gls{elt} is the natural fit: tool output varies widely in structure and evolves frequently, making upfront transformation brittle.

Full re-ingestion does not scale for enterprise environments with thousands of repositories and dozens of security tools. Incremental ingestion pulls only records that are new or changed since the last synchronization. The high-water mark pattern tracks a timestamp or cursor per source, resuming extraction from the last known position. \Gls{cdc} captures changes at the source level, propagating inserts, updates, and deletes as events~\cite{Reis2022}. Both approaches reduce \gls{api} call volume and processing time, enabling more frequent pipeline runs without proportional resource growth.

Source tools change their \glspl{api} and output formats regularly. A rigid schema definition would break pipelines with every upstream change. Schema-on-read stores raw data in its original structure and applies schema interpretation at query time. Additive schema evolution allows new fields to be absorbed without breaking existing queries or downstream consumers~\cite{Lee2024}. For security tool integration, this flexibility is essential: tools add new finding attributes, rename fields, and change enumerations across versions.

Pipeline re-runs must produce the same result regardless of how many times they execute. This idempotency property is essential for handling retries after partial failures and for reprocessing historical data without creating duplicates. Data quality enforcement complements idempotency through validation at each pipeline layer: schema conformance at ingestion, value range checks during normalization, and referential integrity at aggregation. Records that fail validation are routed to quarantine tables rather than silently dropped or propagated downstream~\cite{DAMA2017}. This quarantine pattern ensures zero silent data loss: every ingested record is either successfully processed or isolated with a documented failure reason.

%%% 1.5.3 %%%

\subsection{Domain Data Model}
\label{sec:data-entities}

The security domains analyzed in \autoref{sec:app-inventory} through \autoref{sec:source-integration-summary} produce data about a common set of entities and relationships. Before designing physical schemas, a vendor-agnostic conceptual model must define what the framework represents. This subsection identifies the core entities, their relationships, and the consumption patterns that drive the serving layer.

Five primary entity types form the backbone of the domain model:
\begin{itemize}
    \item \textbf{Applications} carry business context from asset inventories (\autoref{sec:app-inventory}): name, owning team, criticality tier, lifecycle status, and compliance scope. An application represents a business-level unit that may span multiple repositories and deployment environments.
    \item \textbf{Repositories} represent technical assets from \gls{scm} platforms (\autoref{sec:sw-dev-analysis}): code location, primary language, visibility, activity indicators, and archive status. The repository is the primary unit around which security findings are grouped.
    \item \textbf{Findings} capture security issues from any tool category analyzed in \autoref{sec:static-appsec} and \autoref{sec:dynamic-appsec}: severity, status, source tool, detection timestamp, affected code location, and rule or check identifier. Each finding traces to a specific tool scan.
    \item \textbf{Vulnerabilities} are \gls{cve}-identified issues enriched with three signals: \gls{cvss} severity from the \gls{nvd}, exploitation probability from \gls{epss}, and confirmed exploitation status from \gls{cisa} \gls{kev}. Multiple findings from different tools may reference the same vulnerability.
    \item \textbf{Teams} provide organizational ownership, linking personnel to applications and remediation responsibilities. Team structure enables filtering and aggregation by organizational unit.
\end{itemize}

Several additional entity types provide the development process and supply chain context necessary for actionable security analytics:
\begin{itemize}
    \item \textbf{Commits} record individual code changes with author, timestamp, and affected files. They link findings to specific code versions and establish authorship for attribution.
    \item \textbf{Pull requests} represent code change proposals where security scans typically execute. Scan results are often reported per pull request, making it a natural grouping unit for new findings.
    \item \textbf{Pipeline runs} capture \gls{cicd} execution records: which security tools ran, when, against which commit, and whether security gates passed. They indicate scan coverage and tool health across repositories.
    \item \textbf{Issues} track remediation work items in systems such as Jira. Linking findings to issues enables \gls{mttr} calculation and \gls{sla} compliance monitoring.
    \item \textbf{Dependencies} represent third-party libraries identified through \gls{sca}: package name, version, license, and associated \gls{cve} identifiers. They connect \gls{sca} findings to the specific library version that introduced the vulnerability.
    \item \textbf{Branch protection policies} capture governance configurations from \gls{scm} platforms: required reviewers, mandatory status checks, and merge restrictions. They serve as indicators of development process maturity and security hygiene at the repository level.
\end{itemize}

These entities connect through a network of relationships. The application-to-repository mapping is the most critical: it links technical findings to business context, enabling risk-aware prioritization. This relationship is many-to-many; shared libraries serve multiple applications, and microservice applications span multiple repositories. Teams own applications, establishing the chain from organizational accountability through business applications to technical assets and their findings.

Development process entities add temporal and workflow context to this core chain. Repositories contain commits and pull requests, which trigger pipeline runs and produce findings. Findings that reference \gls{cve} identifiers link to vulnerability records, enabling enrichment with external intelligence. Dependencies bridge repositories and vulnerabilities: an \gls{sca} finding links a specific library version in a repository to a known \gls{cve}. Issues track the remediation of one or more findings, closing the loop from detection to resolution.

The entity structure maps naturally to dimensional modeling patterns~\cite{Kimball2013}. Findings function as fact records: measurable events with severity, detection date, and tool source. Applications, repositories, and teams serve as dimension records that provide descriptive context for analysis. Supporting entities such as commits, pull requests, and pipeline runs add temporal and process dimensions. This alignment means standard analytical techniques (filtering by dimension, aggregating facts, computing trends over time) apply directly to the security domain. When multiple tools detect the same underlying issue, cross-tool deduplication collapses related findings while preserving traceability to each source report.

Different stakeholders consume this data through different access patterns. Application owners need aggregated risk dashboards showing finding counts by severity, remediation progress, and compliance status for their applications. Developers need actionable findings with code-level context, delivered through issue trackers. Security experts need drill-down access to raw findings, audit trails, and cross-tool correlation for triage. Leadership needs executive metrics: \gls{mttr}, \gls{sla} compliance rates, vulnerability density trends, and portfolio-level comparisons. These consumption patterns span the \gls{olap} and \gls{oltp} serving requirements identified in \autoref{sec:data-architecture} and drive the serving architecture designed in \autoref{ch:framework}.

\section{Related Work and Gap Analysis}
\label{sec:related-work}

Despite the maturity of individual security tools analyzed in the preceding sections, no standard approach exists for consolidating their output into a unified data platform. Organizations face a fragmented landscape of partial solutions, each addressing a subset of the integration challenge. This section surveys existing approaches, evaluates the closest platform-native offering, and identifies the research gap this thesis addresses.

%%% 1.6.1 %%%

\subsection{Existing Approaches}
\label{sec:existing-approaches}

\textcite{Gartner2023ASPM} define \gls{aspm} as a category of tools that continuously manage application risk through the collection, analysis, and prioritization of security issues across the software lifecycle. Commercial platforms such as Apiiro, Cycode, ArmorCode, and Snyk AppRisk aggregate findings from multiple tools into unified dashboards with correlation and risk scoring. However, they are proprietary, operate as black boxes, and create vendor lock-in: organizations cannot customize data pipelines, apply their own \gls{ml} models, or extend integrations beyond vendor-supported options.

Platform-native security features offer another partial solution. GitHub Advanced Security provides code scanning via CodeQL, secret scanning, and dependency review within the GitHub ecosystem~\cite{GitHubGHAS2025}. GitLab bundles \gls{sast}, \gls{dast}, dependency scanning, container scanning, and a security dashboard into its platform~\cite{GitLabSecurity2025}. Both approaches are ecosystem-locked: they aggregate findings only from their own scanners. Organizations using multiple \gls{scm} platforms or third-party security tools cannot consolidate findings through these native dashboards.

DefectDojo~\cite{DefectDojo2024} is the most prominent open-source alternative, supporting imports from over 150 tools through format-specific parsers. However, it was designed as a vulnerability management interface, not a data platform. Its PostgreSQL backend limits enterprise-scale analytics, and advanced \gls{api} connectors are available only in the commercial offering. \Gls{ocsf}~\cite{OCSF2024} standardizes security event schemas for \gls{siem} and \gls{soar} use cases but does not model application-level entities such as repositories, applications, or development teams.

In practice, many enterprises build ad-hoc integrations: custom scripts that pull data from security tool \glspl{api}, \gls{etl} pipelines that load findings into data warehouses, and dashboards assembled from manual exports. These solutions are fragile. They lack schema governance, break when source \glspl{api} change, and encode institutional knowledge in unmaintained code. Each organization reinvents the same integration patterns without reusable abstractions or standard architectures.

%%% 1.6.2 %%%

\subsection{Databricks Lakewatch}
\label{sec:lakewatch}

Databricks announced Lakewatch in March 2026 as an open, agentic \gls{siem} built natively on the Databricks lakehouse~\cite{Databricks2026Lakewatch}. The platform unifies security, \gls{it}, and business data in a single governed environment powered by Delta Lake and Unity Catalog. Key capabilities include agentic triage (\gls{ai} agents that parse and enrich telemetry across formats), Detection-as-Code (version-controlled detection rules), and an open ecosystem with integrations from security vendors including Wiz, Palo Alto Networks, Okta, and Zscaler.

Lakewatch and the framework proposed in this thesis address different security domains. Lakewatch focuses on runtime security operations: threat detection, incident response, alert triage, and log analytics. The framework focuses on application security posture: vulnerability findings from \gls{sast}, \gls{sca}, \gls{dast}, secret scanning, container scanning, and \gls{iac} tools, combined with remediation tracking and risk aggregation. Their data sources differ accordingly: Lakewatch ingests security logs and telemetry, while the framework ingests security tool findings and application metadata.

The two systems are complementary rather than competing. Shared lakehouse infrastructure enables data exchange: Lakewatch could consume the framework's application risk scores as enrichment context for incident triage, while the framework could ingest Lakewatch's runtime detections as an additional finding source. Together, they cover both proactive posture management and reactive threat detection.

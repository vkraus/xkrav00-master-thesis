\chapter{Analysis}
\label{ch:analysis}

The analysis starts from the data that an application security platform has to integrate: inventories, development systems, security tools, vulnerability intelligence, and runtime telemetry. For each area, the chapter identifies the relevant interfaces, data models, and integration patterns. Technology choices are made later in the \hyperref[ch:framework]{Framework} and \hyperref[ch:implementation]{MVP Implementation} chapters.

\section{Asset Discovery and Inventory}
\label{sec:app-inventory}

Asset discovery and inventory provide the first required context for an application security data platform. Organizations maintain application inventories in a \gls{cmdb} or custom catalog, while cloud providers and container orchestrators expose asset inventories through \glspl{api}. Without this context, a vulnerability cannot be attributed to an owner, scored for business impact, or prioritized.

%%% 1.1.1 %%%

\subsection{Application Portfolio Management}

Enterprise organizations maintain catalogs of business applications with metadata such as name, description, ownership, lifecycle status, and relationships to other assets~\cite{AXELOS2019}. These registries also carry criticality tiers (Tier~1 mission critical, Tier~2 important, Tier~3 noncritical) derived from business impact assessments along the \gls{cia} triad~\cite{Stallings2024, NIST_FIPS199_2004} and regulatory scope flags.

The attribute that matters most for data integration is the mapping from business applications to their technical assets: a single application may span repositories, microservices, infrastructure, and deployment environments. When the framework ingests a vulnerability from a \gls{sast} scanner linked to a repository, this mapping determines which application is affected, who owns it, and how critical it is.

%%% 1.1.2 %%%

\subsection{Configuration Management Databases}

ServiceNow is widely deployed as a \gls{cmdb} platform in enterprise environments and leads the global \gls{itsm} market with over 44\% share~\cite{Gartner2024ITSM}, the closest available proxy for \gls{cmdb} adoption. It serves as the reference platform for this thesis. A \gls{cmdb} organizes all managed assets as \glspl{ci}, each with attributes describing its type, status, and ownership~\cite{AXELOS2019}.

ServiceNow arranges \glspl{ci} in a class hierarchy rooted at the \inlinecode{cmdb\_ci} base table. Each subclass inherits base attributes (name, \inlinecode{sys\_id}, operational status, environment) and adds domain specific fields. For application inventory purposes, the most relevant class is \inlinecode{cmdb\_ci\_business\_app} (Business Application), which extends the base \gls{ci} with attributes such as version, business unit, used for classification, and references to the owning support group~\cite{ServiceNowCMDB2024}. The \gls{mvp} pipeline ingests this class together with \inlinecode{cmdb\_rel\_ci}.

Beyond the application record itself, the \gls{cmdb} captures relationships between \glspl{ci} through a dedicated relationship table (\inlinecode{cmdb\_rel\_ci}). These model dependencies such as ``runs on'' (application to server), ``depends on'' (application to database), and ``hosted on'' (application to cloud service). The most valuable relationships for the framework are those linking business applications to technical assets corresponding to entities in the security data: repository names, deployment targets, and infrastructure components. ServiceNow allows custom attributes and relationship types, so available fields vary between deployments.

%%% 1.1.3 %%%

\subsection{Integration Options}

Integrating \gls{cmdb} data requires choosing between two strategies: pulling data from ServiceNow via its \glspl{api}, or pushing data from a custom ServiceNow application to an external target.

\subsubsection{ServiceNow APIs}

ServiceNow exposes two \gls{rest} \glspl{api} for \gls{cmdb} extraction. The Table \gls{api} (\inlinecode{/api/now/table/\{tableName\}}) provides generic queries against any table with server side filtering, field selection, and pagination~\cite{ServiceNowTableAPI2024}. The \gls{cmdb} Instance \gls{api} (\inlinecode{/now/cmdb/instance/\{className\}}) understands the \gls{ci} class hierarchy and retrieves a \gls{ci} with its relationships in a single call~\cite{ServiceNowCMDB2024}. Authentication is Basic auth with a service account or OAuth~2.0~\cite{ServiceNowRESTAuth2024}, and the \inlinecode{sys\_updated\_on} timestamp serves as a reliable high water mark for incremental extraction.

\subsubsection{ServiceNow Application}

An alternative is to push from the source. A scoped ServiceNow application can use Outbound REST Messages on a schedule, or expose a Scripted \gls{rest} \gls{api}~\cite{ServiceNowScriptedREST2024} that prejoins application records with relationships in one response. The advantage is full access to ServiceNow scripting and relationship traversal. The disadvantage is that development and maintenance live inside ServiceNow, with schema changes coordinated across two platforms. This approach suits organizations with mature ServiceNow development teams.

\subsubsection{Integration Challenges}

The application inventory is the least standardized integration among all data sources. Security testing tools converge around common \gls{api} patterns and formats, but each organization structures its application inventory differently: hierarchy, granularity of asset mapping, and captured attributes vary substantially~\cite{AXELOS2019}. This makes the inventory connector hardest to generalize and most likely to require customization.

Data quality in \glspl{cmdb} is a persistent concern~\cite{Gartner2021CMDB}. Records are often incomplete or stale. A common case is a decommissioned application still listed as active with no current owner. Integrations must account for these issues through validation rules and defaults that flag problems without blocking the pipeline.

Despite these difficulties, the application inventory is indispensable: without its business context, findings lack organizational meaning for prioritization and governance.

Alternative platforms include BMC Helix, Device42, and the open source Ralph. Cloud native services such as AWS Config and Azure Resource Graph expose equivalent inventories for cloud resources, consumed through provider native \glspl{api} with IAM scoped credentials. The bronze ingestion pattern from the \hyperref[ch:framework]{Framework} chapter applies to any source with an inventory \gls{api}.

\section{Software Development}
\label{sec:sw-dev-analysis}

Repositories, build pipelines, and issue trackers form the second major data source category~\cite{Sommerville2015, Pressman2019}. These platforms share a common integration pattern: \gls{rest} over \gls{json}, authentication via OAuth tokens, \glspl{pat}, or service accounts, page or cursor pagination, and rate limits that require backoff. This consistency enables shared connector logic.

%%% 1.2.1 %%%

\subsection{Source Code Management}

For this thesis, the repository is the primary entity around which findings are grouped~\cite{Chacon2014, Skoulikari2024, Winters2020}.

Development teams host Git repositories on cloud \gls{scm} platforms. GitHub is dominant (81\% adoption for code collaboration), followed by GitLab (36\%), Bitbucket, and Azure DevOps~\cite{StackOverflow2025, GitHub2025Octoverse}. Most large organizations run several platforms, so multi platform ingestion is a practical requirement.

Beyond source code, \gls{scm} platforms expose security relevant metadata: primary language, last activity, visibility, archive status. Branch protection rules indicate development process maturity. Team and contributor assignments establish ownership feeding into the mapping from application to team in the \hyperref[sec:app-inventory]{Asset Discovery and Inventory section}.

These platforms share three API patterns: token based authentication (OAuth or \glspl{pat}), page or cursor pagination, and rate limits that require backoff. GitHub also exposes a GraphQL endpoint alongside its \gls{rest} \gls{api} (v3), with a 5\,000 requests per hour limit~\cite{GitHubAPI2024, GitHubRateLimits2024}. GitLab, Bitbucket, and Azure DevOps Repos provide comparable interfaces.

%%% 1.2.2 %%%

\subsection{Continuous Integration and Delivery}

Application security is fundamentally about securing the \gls{sdlc}: \gls{cicd} pipelines are the spine of the modern \gls{sdlc} and each stage can integrate security tools~\cite{Forsgren2018}. The dominant platforms are GitHub Actions, Jenkins, GitLab CI, and Azure Pipelines~\cite{JetBrains2025CICD}. Many organizations run more than one, so the multi platform pattern from \gls{scm} repeats here.

\Gls{cicd} platforms provide contextual data about security scans. Pipeline definitions reveal which tools run. Build results show whether gates passed. Execution metadata records commit, timing, and duration. A repository whose last scan ran three months ago, or whose scans consistently fail, signals coverage gaps and tool health. This is operational context rather than a primary finding source.

Integration patterns vary across \gls{cicd} platforms more than across \gls{scm}: GitHub Actions and Azure Pipelines expose \gls{rest} \glspl{api}, Jenkins uses an \gls{xml} based \gls{api}, and GitLab CI piggybacks on the GitLab \gls{api}. Retrieved data is structurally similar across them: pipeline identifiers, run statuses, timestamps, and commit references. None of these is built as a connector in the reference implementation.

%%% 1.2.3 %%%

\subsection{Issue Tracking}

Issue trackers record remediation status. When a finding is assigned for remediation, an issue is created in the tracker for the team manually or through automation. The framework reads issue status to determine whether a finding is under active remediation, who is responsible, and whether it has been resolved within the \gls{sla} window.

Jira is the dominant enterprise issue tracker. The 2025 Stack Overflow Developer Survey reports Jira at 46\% adoption, behind only GitHub (81\%) and ahead of GitLab (36\%)~\cite{StackOverflow2025}. Azure DevOps Work Items serves the Microsoft ecosystem. GitHub Issues and GitLab Issues provide lightweight built in tracking tied to their \gls{scm} platforms. Many organizations use multiple trackers across teams.

These platforms expose \gls{rest} \glspl{api} with \gls{json} responses and paginated results, and most support webhooks for real time status change notifications. None is built as a connector in the reference implementation. 

Integration is bidirectional: the framework reads remediation status and may create new issues when findings require attention. This raises idempotency concerns (avoiding duplicate issue creation) and state synchronization (keeping the view of the framework consistent with the tracker).

\section{Static Application Security}
\label{sec:static-appsec}

Application security covers practices and tools for identifying vulnerabilities throughout the software lifecycle~\cite{Anderson2020, Stallings2024}. \textcite{McGraw2006} advocated for security touchpoints spanning development. The DevSecOps approach~\cite{Mack2023, Kim2021} realizes this by embedding security testing into \gls{cicd} pipelines. \Gls{sast} examines source code, \gls{sca} checks third party dependencies, secret scanners flag leaked credentials, and \gls{dast} probes running applications. These tools produce large volumes of data in different \glspl{api}, formats, and severity models. The \gls{owasp} Top~10 classifies common web application risks~\cite{OWASP2021} but does not define a data interchange standard.

Several cross cutting standards bring partial consistency. The \gls{cve} system assigns unique identifiers to known vulnerabilities~\cite{MITRE2024}. \Gls{cwe} classifies weakness types~\cite{CWE2024}. \Gls{cvss} scores attack vector, complexity, and impact on a 0--10 scale~\cite{FIRST2019}. \Gls{epss} adds a predictive signal~\cite{Jacobs2020}: the \gls{ml} computed probability that a vulnerability will be exploited within 30~days. \Gls{cisa} maintains the \gls{kev} catalog~\cite{CISAKEV2024}, which adds a third signal: confirmed active exploitation from real world incidents.

For data interchange, \gls{sarif} defines a \gls{json} based format for static analysis results~\cite{OASIS2024}. CycloneDX and \gls{spdx} provide \gls{sbom} schemas~\cite{CycloneDX2024, SPDX2024}. \Gls{ocsf} standardizes security event exchange for \gls{siem} and \gls{soar} use cases~\cite{OCSF2024}. No single format covers all tool categories:
\begin{itemize}
    \item \gls{sarif} addresses static analysis but not \gls{sca} or runtime findings.
    \item CycloneDX and \gls{spdx} cover software composition, not code level vulnerabilities.
    \item \gls{ocsf} serves security operations, not application security posture.
\end{itemize}
This gap motivates the normalization model in the \hyperref[ch:framework]{Framework} chapter.

Static analysis tools examine source code and build artifacts without executing the application. Their findings point to repositories, files, and lines, so developers own them directly. Mobile application security testing is excluded, as the framework targets web applications and backend services.

%%% 1.3.1 %%%

\subsection{Static Application Security Testing}

\Gls{sast} examines source code, bytecode, or binary code without executing the program. \textcite{Chess2007} cover taint analysis, control flow analysis, and pattern matching for injection flaws, buffer overflows, and insecure data handling. Broader rule sets catch more issues and generate more noise. That is the central \gls{sast} tradeoff.

Server tools (SonarQube, Checkmarx, Fortify) expose a \gls{rest} \gls{api}. \gls{cli} tools (Semgrep) produce \gls{json} or \gls{sarif} files. Platform integrated scanners (GitHub Code Scanning, GitLab \gls{sast}) report through the host \gls{scm} \gls{api}. When a platform scanner and a standalone tool both scan a repository, the overlap requires deduplication.

Findings include a rule identifier, file path and line number, severity, code snippet, and remediation guidance. Severity models differ: SonarQube uses five levels (blocker, critical, major, minor, info), Semgrep and Checkmarx use three (high, medium, low). Severity normalization is therefore a core transformation.

%%% 1.3.2 %%%

\subsection{Software Composition Analysis}

\Gls{sca} identifies known vulnerabilities in third party dependencies. Modern applications pull in hundreds of transitive dependencies~\cite{Anderson2020}, any of which can introduce a vulnerability. \textcite{Ohm2020} cover supply chain attacks including typosquatting, dependency confusion, and malicious package injection. \gls{sca} tools analyze dependency manifests, resolve the full tree, and cross reference versions against vulnerability databases such as the \gls{nvd}.

Tools fall into three groups by integration: server platforms (\gls{owasp} Dependency-Track, Snyk) with a \gls{rest} \gls{api}, platform integrated scanners (Dependabot through GitHub GraphQL, GitLab dependency scanning) reached through the host \gls{api}, and \gls{cli} alternatives such as \gls{owasp} Dependency-Check that write \gls{json} or \gls{xml} reports from \gls{cicd} runs. Many tools also generate \glspl{sbom} in CycloneDX or \gls{spdx} format~\cite{CycloneDX2024, SPDX2024}, increasingly required by regulators~\cite{NTIA2021}.

\gls{sca} output is more standardized than other categories because the underlying data comes from shared public databases (\gls{cve}, \gls{nvd}). Findings include the vulnerable dependency name and version, a \gls{cve} identifier, a \gls{cvss} score, the fixed version when available, and exploitability metadata. Tools may resolve the same dependency tree differently, so two scanners flag inconsistent \glspl{cve}. The framework handles this during deduplication: the same \gls{cve} reported by multiple tools against the same repository likely represents a single issue. The \gls{slsa} framework~\cite{SLSA2024} complements \gls{sca} by verifying the integrity and provenance of build artifacts.

%%% 1.3.3 %%%

\subsection{Secret Detection}

Secret detection tools scan version control history for credentials, \gls{api} keys, tokens, and other sensitive material. Once committed, a secret persists in Git history even after deletion from the working tree. Two techniques apply: regex patterns against known credential formats, and entropy scoring against unusually random strings. The entropy approach catches novel formats at higher false positive rates.

\gls{cli} tools (TruffleHog, GitLeaks, detect-secrets) write \gls{json} reports parsed as artifacts. Commercial servers (GitGuardian) expose a \gls{rest} \gls{api}. Platform integrated scanners (GitHub Secret Scanning, GitLab Secret Detection) report through the host \gls{api}~\cite{GitHubAPI2024} but only cover repositories on their own platform. There is no standard output format. Each tool defines its own \gls{json} schema, none supports \gls{sarif}. Findings include secret type, file path, commit reference, and sometimes validity status, but field names and structures vary.

\section{Dynamic Application Security Testing}
\label{sec:dynamic-appsec}

\Gls{dast} tests running applications by sending crafted \gls{http} requests and analyzing responses for vulnerability indicators~\cite{Stuttard2011}. It requires a deployed application and detects vulnerabilities that appear only at runtime, such as authentication bypass, server misconfiguration, and injection flaws. This section covers active scanning. The \hyperref[sec:runtime-security]{Runtime Security section} covers passive telemetry.

The representative tools are \gls{owasp} \gls{zap} (open source) and Burp Suite Enterprise, both exposing a \gls{rest} \gls{api} for scan management and alert retrieval. Findings include the target \gls{url}, affected \gls{http} parameter, vulnerability type mapped to \gls{cwe}~\cite{CWE2024}, exploitation evidence, and confidence rating. The core integration challenge is that \gls{dast} findings are \gls{url} based, not code based. Mapping them to source repositories requires deployment metadata or inventory data from the \hyperref[sec:app-inventory]{Asset Discovery and Inventory section}. Without that link, \gls{dast} findings can be attributed to applications but not to teams or code locations.

\section{Runtime Security}
\label{sec:runtime-security}

Runtime security covers passive telemetry from production workloads, sitting alongside the active scanning in the \hyperref[sec:dynamic-appsec]{Dynamic Application Security Testing section} and completing the three detection tiers the framework uses: static, dynamic, and runtime. The representative tool in this tier is the \gls{waf}. It does not execute scans. It inspects live \gls{http} traffic and emits events when rules fire, marking exploitation attempts against a workload or endpoint and linking to applications through deployment metadata instead of source code coordinates. Broader runtime operations such as \gls{siem} driven incident response and general log analytics are adjacent but out of scope. The framework treats runtime security as one input tier among three, correlated with static and dynamic findings through the shared application inventory.

\Glspl{waf} operate at the network perimeter, inspecting inbound \gls{http} traffic against rule sets such as the \gls{owasp} Core Rule Set~\cite{OWASPCRS2024}. They log blocked and flagged requests with matched rule, request details, and action taken. \gls{aws} \gls{waf} delivers full request logs to Amazon S3 through Kinesis Data Firehose, which the framework consumes as the primary path. The \inlinecode{GetSampledRequests} \gls{api} returns only a sampled subset and serves as a fallback (\href{https://vkraus.github.io/appsec-mvp/connectors/waf/aws-waf/}{source reference}). Cloudflare and Akamai expose comparable \gls{rest} \glspl{api} for log retrieval and configuration.

These platforms bundle \gls{ddos} protection alongside \gls{waf} capabilities. \gls{ddos} mitigation logs traffic patterns, attack signatures, and mitigation actions, providing availability impact data that complements vulnerability findings.

\Glspl{waf} emit append only event streams. The framework projects each event as one finding row on \inlinecode{silver.findings}, with severity derived from the \gls{waf} action and status fixed to \inlinecode{open}.

\section{Source Integration Summary}
\label{sec:source-integration-summary}

The \href{https://vkraus.github.io/appsec-mvp/platform/reference/source-characteristics/}{source characteristics} page tabulates integration characteristics across the AppSec sources surveyed for the thesis.

Several patterns emerge. \gls{rest} \glspl{api} with \gls{json} responses are dominant, but \gls{xml}, GraphQL, \gls{cli} output parsing, and manual uploads are all necessary. Update frequencies range from continuous dependency monitoring to periodic penetration tests. These characteristics define what the ingestion layer in the \hyperref[ch:framework]{Framework} chapter must accommodate.

\section{Data Engineering}

Consolidating the sources above into one analytical platform is a data integration problem. The relevant engineering patterns are lakehouse storage, layered transformation, incremental ingestion, and dual analytical and operational serving.

%%% 1.7.1 %%%

\subsection{Data Platform Architecture}
\label{sec:data-architecture}

Data warehouses~\cite{Inmon2005, Kimball2013} assume structured, stable sources, and security tool output is neither. Data lakes~\cite{Miloslavskaya2016} accept any format through schema on read but risk ``data swamps'' without governance~\cite{DAMA2017}. The lakehouse~\cite{Armbrust2021} combines lake flexibility with warehouse governance through open table formats that add \gls{acid} transactions, schema enforcement, and time travel on top of lake storage~\cite{Lee2024, Thalpati2024}. It accepts semi structured tool output and gives the governance and fast queries needed for dashboards and operational lookups.

The medallion architecture~\cite{Strengholt2025} organizes lakehouse data into three layers:
\begin{itemize}
    \item \textbf{Bronze}: Raw data with minimal transformation, preserving original source schemas.
    \item \textbf{Silver}: Cleaned, validated, and normalized data conforming to a unified schema.
    \item \textbf{Gold}: aggregated metrics and enriched datasets ready for queries.
\end{itemize}
This maps naturally to security data integration. Bronze captures raw tool output in source native schemas, silver normalizes findings into a vendor agnostic model, and gold computes aggregated risk metrics and enriched datasets stakeholders consume.

A security data platform must serve two access patterns. \Gls{olap} queries power dashboards and trend analysis over large aggregated datasets. \Gls{oltp} access supports operational workflows such as issue tracker integration and real time risk lookups, where low latency reads and writes to individual records are essential. Both inform the serving architecture in the \hyperref[ch:framework]{Framework} chapter.

%%% 1.7.2 %%%

\subsection{Data Integration Patterns}
\label{sec:data-integration-patterns}

\textcite{Reis2022} distinguish \gls{etl} from \gls{elt}. \Gls{etl} transforms data before loading, requiring upfront schema knowledge. \Gls{elt} loads raw data first and transforms in place, aligning with lakehouse architectures where distributed compute engines perform transformations at scale~\cite{Thalpati2024}. Security tool output varies and evolves, so upfront transformation breaks. \Gls{elt} fits.

Full reingestion does not scale across thousands of repositories and dozens of tools. Incremental ingestion pulls only new or changed records. The high water mark pattern tracks a timestamp or cursor per source. \Gls{cdc} captures changes at the source level, propagating inserts, updates, and deletes as events~\cite{Reis2022}.

Source \glspl{api} and formats change regularly, so rigid schemas break pipelines on every upstream change. Schema on read stores raw data in its original structure and applies schema at query time. Additive evolution accepts new fields~\cite{Lee2024}, and existing queries keep working.

Reruns are idempotent so retries and replays do not duplicate. Each layer validates: schema at ingest, value ranges at normalization, referential integrity at aggregation. Records that fail validation go to quarantine tables~\cite{DAMA2017}.

Managed ingestion connectors complement manually coded integration. Databricks documents Lakeflow Connect as a managed ingestion service for SaaS applications and databases, governed by Unity Catalog and powered by serverless compute and Lakeflow Spark Declarative Pipelines~\cite{DatabricksLakeflowConnect2025}. Managed connectors are in different release states, so the framework uses them where a supported connector meets the connector contract. The Databricks Labs project Lakeflow Community Connectors~\cite{DatabricksLakeflowCommunityConnectors2026} extends Lakeflow Connect with community maintained connectors built on the Spark Python Data Source \gls{api}. Community connectors were in Beta at thesis submission, are not maintained by Databricks, and do not guarantee forward compatibility~\cite{DatabricksLakeflowCommunityConnectorsDocs2026}. Otherwise the framework falls back to a maintained Python \gls{sdk}, then to \gls{dltool}, then to artifact path consumption.

The mapping from app to repo is the key relationship. It links findings to business context and is many to many: shared libraries serve multiple applications, and microservice applications span multiple repositories. Teams own applications, applications connect to repositories many to many, and findings are produced from pipeline runs against those repositories. Dependencies attach to repositories and reach vulnerabilities through \gls{sca} findings: a finding cites a specific library version and references a known \gls{cve}. Issues track remediation.

The structure maps to dimensional modeling~\cite{Kimball2013}. Findings are facts. Applications, repositories, and teams are dimensions. Commits, pull requests, and pipeline runs add temporal and process dimensions. Cross tool deduplication collapses related findings while preserving traceability to each source.

Stakeholders consume this data through different patterns:
\begin{itemize}
    \item Application owners need aggregated risk dashboards showing finding counts by severity, remediation progress, and compliance status.
    \item Developers need actionable findings with code level context, delivered through issue trackers.
    \item Security experts need drill down access to raw findings, audit trails, and cross tool correlation for triage.
    \item Leadership needs executive metrics: \gls{mttr}, \gls{sla} compliance, vulnerability density trends, and portfolio level comparisons.
\end{itemize}
These span the \gls{olap} and \gls{oltp} requirements from the \hyperref[sec:data-architecture]{Data Platform Architecture section} and drive the serving architecture in the \hyperref[ch:framework]{Framework} chapter.

\section{Related Work and Gap Analysis}
\label{sec:related-work}

No single surveyed approach consolidates application security tool output into the data platform model required here. Organizations face a fragmented set of partial solutions.

%%% 1.8.1 %%%

\subsection{Existing Approaches}

\textcite{Gartner2023ASPM} define \gls{aspm} as tools that continuously manage application risk through collection, analysis, and prioritization of security issues across the software lifecycle. Commercial platforms such as Apiiro, Cycode, ArmorCode, and Snyk AppRisk aggregate findings into unified dashboards with correlation and risk scoring, but they are proprietary. Pipelines cannot be customized, custom \gls{ml} cannot be added, and integrations are limited to what the vendor supports.

Platform native features cover only their own ecosystem. GitHub Advanced Security provides code scanning via CodeQL, secret scanning, and dependency review~\cite{GitHubGHAS2025}. GitLab bundles \gls{sast}, \gls{dast}, dependency scanning, container scanning, and a security dashboard~\cite{GitLabSecurity2025}. Organizations using multiple \gls{scm} platforms or third party tools cannot consolidate through them.

DefectDojo~\cite{DefectDojo2024} is the most prominent open source alternative, supporting imports from over 150 tools through format specific parsers. It was designed as a vulnerability management interface, not a data platform. Its PostgreSQL backend limits enterprise scale analytics, and advanced \gls{api} connectors are commercial only. \Gls{ocsf}~\cite{OCSF2024} standardizes security event schemas for \gls{siem} and \gls{soar} but does not model application level entities such as repositories, applications, or teams.

The direct alternatives therefore leave different gaps relative to the framework of this thesis. Commercial \gls{aspm} platforms address application risk aggregation but keep the data model, connector behavior, and analytics pipeline inside a vendor product~\cite{Gartner2023ASPM}. Platform native features provide strong findings inside one \gls{scm} or DevSecOps ecosystem but do not consolidate mixed toolchains~\cite{GitHubGHAS2025, GitLabSecurity2025}. DefectDojo provides broad parser coverage and vulnerability management workflows, but not a governed lakehouse pipeline from raw source records to analytical and serving tables~\cite{DefectDojo2024}. \Gls{sarif}, CycloneDX, \gls{spdx}, and \gls{ocsf} are valuable interchange standards, but each covers only part of the model needed here: static analysis results, software bills of materials, package metadata, or security events~\cite{OASIS2024, CycloneDX2024, SPDX2024, OCSF2024}. Lakewatch is closest at the data platform level, but its domain is runtime security operations rather than application security posture~\cite{Databricks2026Lakewatch}.

Many enterprises build ad hoc integrations: custom scripts, \gls{etl} pipelines, and dashboards from manual exports. These lack schema governance, break on \gls{api} changes, and persist as institutional knowledge in unmaintained scripts.

%%% 1.8.2 %%%

\subsection{Databricks Lakewatch}
\label{sec:lakewatch}

Databricks announced Lakewatch in March 2026 as an open, agentic \gls{siem} built on the Databricks lakehouse and made it available in Private Preview~\cite{Databricks2026Lakewatch}. It unifies security, \gls{it}, and business data in a single governed environment powered by Delta Lake and Unity Catalog, with agentic triage, Detection as Code, and a partner ecosystem including Wiz, Palo Alto Networks, Okta, and Zscaler.

Lakewatch focuses on runtime security operations: threat detection, incident response, alert triage, and log analytics. This framework focuses on application security posture: findings from \gls{sast}, \gls{sca}, \gls{dast}, secret scanning, and \gls{waf} runtime telemetry, joined to \gls{cmdb} and \gls{scm} context for remediation tracking and risk aggregation. The author did not have access to the Private Preview during thesis preparation, so this comparison is based on Databricks public material rather than hands on evaluation. The two are complementary. Shared lakehouse infrastructure could enable data exchange: Lakewatch could consume application risk scores for incident triage, and the framework could ingest Lakewatch runtime detections as a finding source.

\section{Selected Sources}
\label{sec:selected-sources}

The reference implementation in the \hyperref[ch:implementation]{MVP Implementation} chapter instantiates the framework against nine source systems chosen to cover the ingestion and integration patterns that the framework must support, while keeping the sample small enough to manage. The selection spans all three detection tiers: static testing, dynamic testing, and runtime security.

\subsection{Selection Criteria}

The nine sources are selected based on five criteria:

\begin{enumerate}
    \item \textbf{Open source or free tier available.} The reference implementation must be reproducible without commercial licenses.
    \item \textbf{Full domain coverage across three detection tiers.} The nine together must cover every domain in the framework: \gls{cmdb}, \gls{scm}, and the three detection tiers, namely static testing (\gls{sast}, \gls{sca}, secrets), dynamic testing (\gls{dast}), and runtime security (\gls{waf}).
    \item \textbf{\Gls{api} heterogeneity.} The selection deliberately includes \gls{rest} (ServiceNow, SonarQube, Dependency-Track, GitHub, GitLab, OWASP ZAP, AWS WAF), GraphQL (GitHub, GitLab), and \gls{cli} wrapped (Semgrep, TruffleHog) sources so the connector contract is exercised across integration styles.
    \item \textbf{Limit heterogeneity to nine to maintain scope control.} The nine sources are selected as a design sample. They cover the ingestion and integration patterns needed to exercise the framework while keeping implementation effort manageable. This improves pattern coverage but does not make the sample statistically representative of all enterprise application security sources.
    \item \textbf{Industry adoption.} Each tool is in widespread enterprise use.
\end{enumerate}

The selection therefore supports analytical generalization from observed integration patterns, not statistical generalization from a population of tools. The main bias is toward sources with accessible \glspl{api}, free tiers, and formats that can be exercised in a thesis setting. The \hyperref[sec:conclusion-limitations]{Limitations section} names source categories not demonstrated, including SOAP, gRPC, syslog, Kafka event streams, binary telemetry, and push only webhook native sources.

\subsection{Source Inventory}

The selection resolves to nine sources spanning the three detection tiers, plus a \gls{cmdb} for inventory and an \gls{scm} pair for the framework first dependency.

\begin{itemize}
    \item \textbf{ServiceNow} (\gls{cmdb}). Dominant enterprise \gls{cmdb} with \gls{rest} Table and CMDB Instance \glspl{api} and a native \inlinecode{sys\_updated\_on} high water mark.
    \item \textbf{GitHub} (\gls{scm} plus integrated \gls{sast}, \gls{sca}, secrets). \Gls{rest} and GraphQL \glspl{api} with cursor pagination and rich webhooks.
    \item \textbf{GitLab} (\gls{scm} plus integrated security). \Gls{rest} and GraphQL with keyset and offset pagination. Security findings require Ultimate tier or pipeline artifacts.
    \item \textbf{SonarQube} (\gls{sast}). Mature server product with a \gls{rest} Web \gls{api}, \inlinecode{updateDate} high water mark, and a scan completion webhook.
    \item \textbf{Semgrep} (\gls{sast}). Free \gls{cli} engine deployed in a \gls{cicd} step. Exercises the artifact ingestion pattern.
    \item \textbf{Dependency-Track} (\gls{sca}). \gls{owasp} project with a \gls{rest} \gls{api} and \gls{sbom} centric vulnerability correlation across multiple advisory sources.
    \item \textbf{TruffleHog} (secrets). \Gls{cli} tool with live credential verification that populates the \inlinecode{validity\_status} field.
    \item \textbf{OWASP ZAP} (\gls{dast}). Open source dynamic scanner operated as a daemon with a \gls{rest} \gls{api}~\parencite{OWASPZAP2024}, exercising the on demand scan lifecycle pattern.
    \item \textbf{AWS WAF} (\gls{waf}, runtime). Kinesis Data Firehose to S3 log stream as the primary path~\parencite{AWSWAF2026}, with the \inlinecode{GetSampledRequests} \gls{api} as the time window sampled fallback.
\end{itemize}

\subsection{Cross Source Synthesis}
\label{sec:cross-source-synthesis}

Across the nine sources, four record forms recur (ticket like, resource like, finding like, event like), severity scales span three to six levels, and status vocabularies diverge more sharply with tool specific states that rarely map one to one. Five pagination strategies appear: offset (ServiceNow, SonarQube, Dependency-Track), cursor (GitHub \gls{rest}), GraphQL cursor (GitHub and GitLab GraphQL), keyset (GitLab \gls{rest}), and none (\gls{cli} sources, AWS WAF). The sources also split on an operational pattern axis: periodic global scanners polled via \inlinecode{updated\_at} (SonarQube, Dependency-Track), \gls{cicd} step scanners indexed by commit \gls{sha} (Semgrep, TruffleHog), on demand dynamic scanners read via scan lifecycle \gls{api} (OWASP ZAP), and runtime telemetry sampled over time windows (AWS WAF). Together they exercise all five ingestion strategies the framework prescribes. The \href{https://vkraus.github.io/appsec-mvp/platform/reference/source-capability-matrix/}{capability matrix} tabulates them against the capabilities that matter for connector design.

\section{Requirements Summary}
\label{sec:req-summary}

The analysis above produces the core requirements used by the \hyperref[ch:framework]{Framework} chapter. The complete requirements specification is published in the \href{https://vkraus.github.io/appsec-mvp/}{\gls{mvp} documentation} and attached to this thesis as \texttt{appsec-mvp-docs.zip}. It contains the source \gls{api} analysis, mapping derivations, runbooks, validation logs, and the full traceability matrix. The summary below gives the parts needed to evaluate the requirements contribution without reading the external specification. \autoref{tab:req-summary} names the requirement families, the evidence in the thesis, and the implementation trace used to evaluate each family. \autoref{tab:connector-req-snapshot} lists the stable connector requirement identifiers used by tests and by the published traceability matrix.

The requirement identifiers are intentionally stable across sources. A source can mark a requirement as not applicable (for example, tools that only emit artifacts have no \gls{api} pagination or rate limit handling), but applicable requirements must be bound to tests. This is the bridge between the requirements specification contribution and the implementation evidence: the framework defines the identifiers and expected behavior, while the \hyperref[ch:implementation]{MVP Implementation} chapter reports how the \gls{mvp} satisfies or bounds them for each selected source.

The gap identified above is addressed by a vendor agnostic framework. It applies lakehouse architecture and the medallion pattern to ingest tool output, normalize it into a domain model, and serve it through \gls{olap} and \gls{oltp} interfaces. The \hyperref[ch:framework]{Framework} chapter gives the design, and the \hyperref[ch:implementation]{MVP Implementation} chapter reports the \gls{mvp}.

\chapter{Analysis}
\label{ch:analysis}

This chapter analyzes the functional domains relevant to building an application security data platform. Each section combines theoretical foundations with practical tool and \gls{api} analysis, focusing on source system interfaces, data models, and integration patterns. Technology choices are deferred to \autoref{ch:framework} and \autoref{ch:implementation}.

\section{Asset Discovery and Inventory}
\label{sec:app-inventory}

Asset discovery and inventory is the foundational data source for any application security data platform. Organizations maintain application inventories in a \gls{cmdb} or custom catalog, while cloud providers and container orchestrators expose asset inventories through \glspl{api}. Without this context, a vulnerability cannot be attributed to an owner, scored for business impact, or prioritized.

%%% 1.1.1 %%%

\subsection{Application Portfolio Management}

Enterprise organizations maintain catalogs of their business applications with metadata such as application name, description, ownership information, lifecycle status, and relationships to other assets~\cite{AXELOS2019}.

These registries also capture security relevant attributes. Information security is commonly assessed along the \gls{cia} triad: confidentiality (preventing unauthorized disclosure), integrity (preventing unauthorized modification), and availability (ensuring authorized access)~\cite{Stallings2024}. Business impact assessments evaluate all three \gls{cia} dimensions to produce criticality ratings, commonly structured as tiers: Tier~1 for mission critical applications, Tier~2 for important supporting systems, and Tier~3 for noncritical internal tools~\cite{NIST_FIPS199_2004}. Regulatory scope flags identify which compliance frameworks apply to a given application.

For data integration, the most important attribute is the mapping between business applications and their technical assets. A single business application may span multiple repositories, microservices, infrastructure components, and deployment environments. When the framework ingests a vulnerability from a \gls{sast} scanner linked to a specific repository, this mapping determines which business application is affected, who owns it, and how critical it is, so that prioritization reflects risk.

%%% 1.1.2 %%%

\subsection{Configuration Management Databases}

The most common \gls{cmdb} platform in enterprise environments is ServiceNow, holding over 44\% of the global \gls{itsm} market share~\cite{Gartner2024ITSM}. It serves as the reference platform for this thesis. A \gls{cmdb} organizes all managed assets as \glspl{ci}, each with attributes describing its type, status, and ownership~\cite{AXELOS2019}.

ServiceNow arranges \glspl{ci} in a class hierarchy rooted at the \inlinecode{cmdb\_ci} base table. Each subclass inherits base attributes (name, \inlinecode{sys\_id}, operational status, environment) and adds domain specific fields. For application inventory purposes, the most relevant class is \inlinecode{cmdb\_ci\_business\_app} (Business Application), which extends the base \gls{ci} with attributes such as version, business unit, used for classification, and references to the owning support group~\cite{ServiceNowCMDB2024}. The \gls{mvp} pipeline ingests this class together with \inlinecode{cmdb\_rel\_ci}.

Beyond the application record itself, the \gls{cmdb} captures relationships between \glspl{ci} through a dedicated relationship table (\inlinecode{cmdb\_rel\_ci}). These model dependencies such as ``runs on'' (application to server), ``depends on'' (application to database), and ``hosted on'' (application to cloud service). The most valuable relationships for the framework are those linking business applications to technical assets corresponding to entities in the security data: repository names, deployment targets, and infrastructure components. ServiceNow allows custom attributes and relationship types, so available fields vary between deployments.

%%% 1.1.3 %%%

\subsection{Integration Options}

Integrating \gls{cmdb} data requires choosing between two strategies: pulling data from ServiceNow via its \glspl{api}, or pushing data from a custom ServiceNow application to an external target.

\subsubsection{ServiceNow APIs}

ServiceNow exposes two complementary \gls{rest} \glspl{api} for \gls{cmdb} data extraction. The Table \gls{api} provides generic CRUD operations against any ServiceNow table through the endpoint \inlinecode{/api/now/table/\{tableName\}}~\cite{ServiceNowTableAPI2024}. Responses are \gls{json} formatted, with support for server side filtering (\inlinecode{sysparm\_query}), field selection (\inlinecode{sysparm\_fields}), and pagination via \inlinecode{sysparm\_limit} and \inlinecode{sysparm\_offset} (default maximum of 10\,000~records per request). The \inlinecode{sysparm\_display\_value} parameter resolves reference fields to human readable names instead of internal \inlinecode{sys\_id} values.

The \gls{cmdb} Instance \gls{api} (\inlinecode{/now/cmdb/instance/\{className\}}) provides a \gls{cmdb} aware alternative that understands the \gls{ci} class hierarchy~\cite{ServiceNowCMDB2024}. It retrieves a \gls{ci} with its relationships in a single call, reducing \gls{api} calls needed to reconstruct the mapping from application to asset, but is more constrained in query capabilities than the Table \gls{api}.

Both \glspl{api} require authentication, typically Basic Authentication with a service account granted the \inlinecode{rest\_service} or \inlinecode{cmdb\_read} role, or OAuth~2.0 for more security conscious deployments~\cite{ServiceNowRESTAuth2024}. Rate limits are governed by platform transaction quotas rather than per endpoint limits. For incremental extraction, the \inlinecode{sys\_updated\_on} timestamp present on all records serves as a reliable high water mark~\cite{ServiceNowTableAPI2024}.

Any pull based integration must handle authentication, pagination, rate limiting, and incremental state management. Tooling choices specific to each source are documented on the \href{https://vkraus.github.io/appsec-mvp/connectors/cmdb/servicenow/}{ServiceNow source reference page}.

\subsubsection{ServiceNow Application}

An alternative is to push data from the source. ServiceNow supports scoped applications running on the platform. A custom application can use Outbound REST Messages to send \gls{cmdb} data to an external target (a cloud storage bucket or a \gls{rest} endpoint) on a schedule defined through Scheduled Jobs or Flow Designer. It can also expose a Scripted \gls{rest} \gls{api}~\cite{ServiceNowScriptedREST2024}: a custom endpoint that formats data exactly as the consumer needs it, prejoining application records with relationships and custom attributes in a single response.

The advantage is full access to ServiceNow's scripting, relationship traversal, and business logic without external \gls{api} call overhead. The disadvantage is that development and maintenance happen inside ServiceNow, requiring platform expertise and a separate deployment lifecycle, with schema or logic changes coordinated across two platforms. This approach suits organizations with mature ServiceNow development teams that prefer to own export logic on the source side.

\subsubsection{Integration Challenges}

The application inventory is the least standardized integration among all data sources. Security testing tools converge around common \gls{api} patterns and formats, but each organization structures its application inventory differently: hierarchy, granularity of asset mapping, and captured attributes vary substantially~\cite{AXELOS2019}. This makes the inventory connector hardest to generalize and most likely to require customization.

Data quality in \glspl{cmdb} is a persistent concern~\cite{Gartner2021CMDB}. Records are often incomplete or stale. A common case is a decommissioned application still listed as active with no current owner. Integrations must account for these issues through validation rules and defaults that flag problems without blocking the pipeline.

Despite these difficulties, the application inventory is indispensable: without its business context, findings lack organizational meaning for prioritization and governance.

Alternative platforms include BMC Helix, Device42, and the open source Ralph. Cloud native services such as AWS Config and Azure Resource Graph expose equivalent inventories for cloud resources, consumed through provider native \glspl{api} with IAM scoped credentials. The bronze ingestion pattern (\autoref{ch:framework}) applies to any source with an inventory \gls{api}.

\section{Software Development}
\label{sec:sw-dev-analysis}

Modern software is built collaboratively from source code, organized in repositories, and deployed through automated pipelines~\cite{Sommerville2015, Pressman2019}. Repositories, build pipelines, and issue trackers form the second major data source category for the framework. These platforms share a common integration pattern: \gls{rest} over \gls{json}, authentication via OAuth tokens, \glspl{pat}, or service accounts, offset or cursor pagination, and rate limits that require backoff. This consistency enables shared connector logic.

%%% 1.2.1 %%%

\subsection{Source Code Management}

\textcite{Chacon2014} provide a thorough treatment of Git, covering branching, merging, and distributed workflows. \textcite{Skoulikari2024} offers a more recent visual introduction. \textcite{Winters2020} extend this to organizational scale, describing how large teams manage repositories with thousands of contributors. For this thesis, the repository is the primary entity around which findings are grouped, as detailed in \autoref{ch:framework}.

Development teams host Git repositories on cloud based \gls{scm} platforms. GitHub is dominant, with over 150 million developers and adoption by 92\% of Fortune~100 companies~\cite{GitHub2025Octoverse}. The 2025 Stack Overflow Developer Survey reports GitHub at 81\% adoption for code collaboration, followed by GitLab at 36\%~\cite{StackOverflow2025}. Bitbucket and Azure DevOps serve smaller but significant enterprise segments. Most large organizations run multiple platforms through acquisitions, team preferences, or regulatory splits. Multi platform ingestion is therefore a practical requirement.

Beyond source code, \gls{scm} platforms expose security relevant metadata: primary language, creation and last activity dates, visibility, and archive status. Branch protection rules indicate development process maturity. Team and contributor assignments establish ownership feeding into the mapping from application to team from \autoref{sec:app-inventory}.

GitHub exposes two \glspl{api}~\cite{GitHubAPI2024}: \gls{rest} (v3) with resource oriented endpoints and page based pagination, and GraphQL (v4) with selective field retrieval and cursor pagination. Both share authentication (OAuth tokens or \glspl{pat}) and a rate limit of 5\,000 requests per hour~\cite{GitHubRateLimits2024}. All use token based authentication and \gls{json} responses, enabling shared connector logic.

Other enterprise \gls{scm} platforms expose comparable \gls{rest} (and sometimes GraphQL) \glspl{api}: \href{https://vkraus.github.io/appsec-mvp/connectors/scm/gitlab/}{GitLab}, Bitbucket, and Azure DevOps Repos.

%%% 1.2.2 %%%

\subsection{Continuous Integration and Delivery}

\Gls{sdlc} practices have shifted from sequential models to iterative methodologies and DevOps. \textcite{Forsgren2018} present empirical evidence that high performing teams deploy more frequently with shorter lead times through \gls{cicd} automation. \textcite{Kim2021} provide practical guidance for implementing DevOps pipelines at scale. The \gls{cicd} pipeline is relevant because each stage can integrate security tools.

GitHub Actions is the most adopted \gls{cicd} platform, used by 62\% of developers for personal projects and 41\% in organizational settings~\cite{JetBrains2025CICD}. Jenkins remains prevalent in enterprises at 28\% organizational adoption, followed by GitLab CI at 19\%. 32\% of organizations use two or more \gls{cicd} tools and 9\% use at least three, reinforcing the multiplatform integration challenge seen with \gls{scm} platforms.

\Gls{cicd} platforms provide contextual data about security scans. Pipeline definitions reveal which tools run. Build results show whether gates passed. Execution metadata records commit, timing, and duration. This is operational context rather than a primary finding source: a repository whose last scan ran three months ago, or whose scans consistently fail, signals coverage gaps and tool health.

Integration patterns vary more across \gls{cicd} platforms than across \gls{scm} tools. GitHub Actions and Azure Pipelines expose \gls{rest} \glspl{api} with \gls{json} responses, Jenkins uses an \gls{xml} based \gls{api} with a different authentication model, and GitLab CI piggybacks on the GitLab \gls{api}. Despite these differences, retrieved data is structurally similar: pipeline identifiers, run statuses, timestamps, and commit references. None of these \gls{cicd} platforms is built as a connector in the reference implementation.

%%% 1.2.3 %%%

\subsection{Issue Tracking}

Issue trackers record remediation status. When a finding is assigned for remediation, an issue is created in the tracker for the team manually or through automation. The framework reads issue status to determine whether a finding is under active remediation, who is responsible, and whether it has been resolved within the \gls{sla} window.

Jira is the dominant enterprise issue tracker. The 2025 Stack Overflow Developer Survey reports Jira at 46\% adoption, behind only GitHub (81\%) and ahead of GitLab (36\%)~\cite{StackOverflow2025}. Azure DevOps Work Items serves the Microsoft ecosystem. GitHub Issues and GitLab Issues provide lightweight built in tracking tied to their \gls{scm} platforms. Many organizations use multiple trackers across teams.

These platforms expose \gls{rest} \glspl{api} with \gls{json} responses and paginated results, and most support webhooks for real time status change notifications. None is built as a connector in the reference implementation. 

Integration is bidirectional: the framework reads remediation status and may create new issues when findings require attention. This raises idempotency concerns (avoiding duplicate issue creation) and state synchronization (keeping the view of the framework consistent with the tracker).

\section{Static Application Security}
\label{sec:static-appsec}

Application security encompasses practices and tools for identifying vulnerabilities throughout the software lifecycle~\cite{Anderson2020, Stallings2024}. \textcite{McGraw2006} advocated for security touchpoints spanning development. The DevSecOps paradigm~\cite{Mack2023, Kim2021} realizes this by embedding security testing into \gls{cicd} pipelines. \Gls{sast} examines source code, \gls{sca} checks third party dependencies, secret scanners flag leaked credentials, and \gls{dast} probes running applications. These tools produce large volumes of data in different \glspl{api}, formats, and severity models. The \gls{owasp} Top~10 classifies common web application risks~\cite{OWASP2021} but does not define a data interchange standard.

Several cross cutting standards bring partial consistency. The \gls{cve} system assigns unique identifiers to known vulnerabilities~\cite{MITRE2024}. \Gls{cwe} classifies weakness types~\cite{CWE2024}. \Gls{cvss} scores attack vector, complexity, and impact on a 0--10 scale~\cite{FIRST2019}. \Gls{epss} adds a predictive signal~\cite{Jacobs2020}: the \gls{ml} computed probability that a vulnerability will be exploited within 30~days. \Gls{cisa} maintains the \gls{kev} catalog~\cite{CISAKEV2024}, which adds a third signal: confirmed active exploitation from real world incidents.

For data interchange, \gls{sarif} defines a \gls{json} based format for static analysis results~\cite{OASIS2024}. CycloneDX and \gls{spdx} provide \gls{sbom} schemas~\cite{CycloneDX2024, SPDX2024}. \Gls{ocsf} standardizes security event exchange for \gls{siem} and \gls{soar} use cases~\cite{OCSF2024}. No single format covers all tool categories:
\begin{itemize}
    \item \gls{sarif} addresses static analysis but not \gls{sca} or runtime findings.
    \item CycloneDX and \gls{spdx} cover software composition, not code level vulnerabilities.
    \item \gls{ocsf} serves security operations, not application security posture.
\end{itemize}
This gap motivates the normalization model in \autoref{ch:framework}.

Static analysis tools examine source code and build artifacts without executing the application. Their findings point to repositories, files, and lines, so developers own them directly. Mobile application security testing is excluded, as the framework targets web applications and backend services.

%%% 1.3.1 %%%

\subsection{Static Application Security Testing}

\Gls{sast} examines source code, bytecode, or binary code without executing the program. \textcite{Chess2007} cover taint analysis, control flow analysis, and pattern matching for detecting injection flaws, buffer overflows, and insecure data handling. Broader rule sets catch more issues and generate more noise~\cite{Chess2007}. That is the central \gls{sast} tradeoff.

SonarQube exposes a \gls{rest} Web \gls{api} (\href{https://vkraus.github.io/appsec-mvp/connectors/sast/sonarqube/}{source reference}), and Semgrep runs as a \gls{cli} tool producing \gls{json} or \gls{sarif} output with an optional Cloud Platform \gls{api} (\href{https://vkraus.github.io/appsec-mvp/connectors/sast/semgrep/}{source reference}). \gls{scm} integrated scanners such as GitHub Code Scanning (CodeQL) and GitLab \gls{sast} report through the host \gls{scm} \gls{api}. Commercial alternatives include Checkmarx and Fortify, both exposing \gls{rest} \glspl{api}. When platform native and standalone tools scan the same repository, the overlap requires deduplication in the normalization layer.

Findings typically include a rule identifier, affected file path and line number, severity, code snippet, and remediation guidance. Severity models differ. SonarQube uses a five level scale (blocker, critical, major, minor, info). Semgrep and Checkmarx use high, medium, and low, sometimes with a numerical score. Severity normalization is therefore a core transformation. \autoref{ch:implementation} resolves SonarQube and Semgrep to ingestion categories and publishes their reference pages per source. Only the ServiceNow and GitHub connectors are built as working code at \gls{mvp} time.

%%% 1.3.2 %%%

\subsection{Software Composition Analysis}

\Gls{sca} identifies known vulnerabilities in third party dependencies. Modern applications pull in hundreds of transitive dependencies~\cite{Anderson2020}, any of which can introduce a vulnerability. \textcite{Ohm2020} provide a systematic review of supply chain attacks including typosquatting, dependency confusion, and malicious package injection. \gls{sca} tools analyze dependency manifests, resolve the full tree, and cross reference versions against vulnerability databases such as the \gls{nvd}.

\gls{owasp} Dependency-Track is an open source platform that ingests \glspl{sbom} in CycloneDX or \gls{spdx} format and exposes a \gls{rest} \gls{api} (\href{https://vkraus.github.io/appsec-mvp/connectors/sca/dependency-track/}{source reference}). Snyk exposes a \gls{rest} \gls{api}, and Dependabot exposes alerts through the GitHub GraphQL \gls{api}. Many \gls{sca} tools also generate \glspl{sbom}~\cite{CycloneDX2024, SPDX2024}, increasingly required by regulators~\cite{NTIA2021}. \autoref{ch:implementation} resolves Dependency-Track to \gls{dltool}, and GitHub Dependabot and GitLab dependency scanning are reached through their respective platform \glspl{api}. Only the ServiceNow and GitHub connectors are built as working code at \gls{mvp} time.

\gls{sca} output is more standardized than other categories. The data comes from shared public databases (\gls{cve}, \gls{nvd}). Findings include the vulnerable dependency name and version, a \gls{cve} identifier, a \gls{cvss} score, the fixed version when available, and exploitability metadata. Tools may resolve the same dependency tree differently, so two scanners flag inconsistent \glspl{cve}. The framework handles this during deduplication, recognizing that the same \gls{cve} reported by multiple tools against the same repository likely represents a single issue.

\gls{sca} tools also detect license violations (e.g., GPL licensed code in proprietary applications). The \gls{slsa} framework~\cite{SLSA2024} complements \gls{sca}. \gls{sca} checks whether dependencies contain known vulnerabilities. \gls{slsa} verifies the integrity and provenance of build artifacts.

\gls{owasp} Dependency-Check, a \gls{cli} oriented alternative that writes \gls{json} or \gls{xml} reports from \gls{cicd} runs, fits the same \gls{cli} artifact ingestion pattern as Semgrep's \gls{cli} mode.

%%% 1.3.3 %%%

\subsection{Secret Detection}

Secret detection tools scan version control history for credentials, \gls{api} keys, tokens, and other sensitive material. Once committed, a secret persists in Git history even after deletion from the working tree. Two techniques apply: regex patterns against known credential formats, and entropy scoring against unusually random strings. The entropy approach catches novel formats at higher false positive rates.

TruffleHog is a \gls{cli} tool combining pattern and entropy analysis with live credential verification, producing \gls{json} output parsed as an artifact (\href{https://vkraus.github.io/appsec-mvp/connectors/secrets/trufflehog/}{source reference}). GitLeaks and detect-secrets are similar \gls{cli} oriented alternatives, and commercial offerings such as GitGuardian expose \gls{rest} \glspl{api} for centralized management.

Scanners integrated into the platform differ. GitHub Secret Scanning exposes alerts through the GitHub \gls{rest} \gls{api} with webhook notifications~\cite{GitHubAPI2024}, and GitLab Secret Detection reports through GitLab's security dashboard and \gls{api}. These are simpler to integrate because they reuse platform \glspl{api} but cover only repositories on their own platforms.

There is no standard output format. Each tool defines its own \gls{json} schema, and none supports \gls{sarif}. Findings include secret type, file path, commit reference, and sometimes validity status, but field names and structures vary.

\section{Dynamic Application Security Testing}
\label{sec:dynamic-appsec}

Dynamic application security testing operates on running applications by actively issuing requests and evaluating responses. Unlike static analysis, it requires a deployed instance and detects flaws that manifest only at execution time: authentication bypass, server misconfiguration, and certain injection classes. This section covers active scanning. \autoref{sec:runtime-security} covers passive telemetry. The cross cutting standards from \autoref{sec:static-appsec} apply equally to dynamic findings.

%%% 1.4.1 %%%

\subsection{Dynamic Application Security Testing}

\Gls{dast} tests running applications by sending crafted \gls{http} requests and analyzing responses for vulnerability indicators~\cite{Stuttard2011}. Unlike \gls{sast}, \gls{dast} requires a deployed application and detects vulnerabilities that manifest only at runtime, such as authentication bypass, server misconfiguration, and certain injection flaws.

\gls{owasp} \gls{zap} is the most widely used open source \gls{dast} tool, exposing a \gls{rest} \gls{api} for scan management and alert retrieval (\href{https://vkraus.github.io/appsec-mvp/connectors/dast/owasp-zap/}{source reference}). Burp Suite Enterprise exposes a \gls{rest} \gls{api}, while the Professional edition is a desktop tool without programmatic access. Findings include the target \gls{url}, affected \gls{http} parameter, vulnerability type mapped to \gls{cwe}~\cite{CWE2024}, exploitation evidence, and confidence rating.

The core integration challenge is that \gls{dast} findings are \gls{url} based, not code based. Mapping \gls{url} based findings to source repositories requires deployment metadata or inventory data from \autoref{sec:app-inventory}. Without this, \gls{dast} findings can be attributed to applications but not to development teams or code locations.

\section{Runtime Security}
\label{sec:runtime-security}

Runtime security covers passive telemetry from production workloads, sitting alongside the active scanning in \autoref{sec:dynamic-appsec} and completing the three detection tiers the framework uses: static, dynamic, and runtime. The representative tool in this tier is the \gls{waf}. It does not execute scans. It inspects live \gls{http} traffic and emits events when rules fire, marking exploitation attempts against a workload or endpoint and linking to applications through deployment metadata rather than source code coordinates. Broader runtime operations such as \gls{siem} driven incident response and general log analytics are adjacent but out of scope. The framework treats runtime security as one input tier among three, correlated with static and dynamic findings through the shared application inventory.

%%% 1.5.1 %%%

\subsection{Web Application Firewalls}

\Glspl{waf} operate at the network perimeter, inspecting inbound \gls{http} traffic against rule sets such as the \gls{owasp} Core Rule Set~\cite{OWASPCRS2024}. They log blocked and flagged requests with matched rule, request details, and action taken. \gls{aws} WAF exposes the \inlinecode{GetSampledRequests} \gls{api} as the primary interface, with CloudWatch Logs as an opt in extension for deployments requiring full fidelity logging (\href{https://vkraus.github.io/appsec-mvp/connectors/waf/aws-waf/}{source reference}). Cloudflare and Akamai expose comparable \gls{rest} \glspl{api} for log retrieval and configuration.

These platforms bundle \gls{ddos} protection alongside \gls{waf} capabilities. \gls{ddos} mitigation logs traffic patterns, attack signatures, and mitigation actions, providing availability impact data that complements vulnerability findings.

\Glspl{waf} emit event streams, not discrete findings. The framework consumes aggregated patterns, not raw logs.

\subsection{Source Integration Summary}
\label{sec:source-integration-summary}

The \href{https://vkraus.github.io/appsec-mvp/platform/reference/source-characteristics/}{source characteristics reference page} tabulates integration characteristics across the AppSec source landscape surveyed for the thesis.

Several patterns emerge. \gls{rest} \glspl{api} with \gls{json} responses are dominant, but \gls{xml}, GraphQL, \gls{cli} output parsing, and manual uploads are all necessary. Standardization varies: \gls{sca} benefits from the \gls{cve}/\gls{nvd} ecosystem, \gls{sast} is partially standardized through \gls{sarif}, and secret scanning has no standard format. Update frequencies range from continuous dependency monitoring to periodic penetration tests. These characteristics define what the ingestion layer in \autoref{ch:framework} must accommodate.

\section{Data Engineering}

Consolidating the diverse sources analyzed above into a unified analytical platform is a data integration problem. This section surveys the architectural paradigms and engineering patterns relevant to solving it.

%%% 1.5.1 %%%

\subsection{Data Platform Architecture}
\label{sec:data-architecture}

The literature documents a progression from data warehouses through data lakes to the lakehouse. \textcite{DAMA2017} provide the data management body of knowledge. The data warehouse, formalized by \textcite{Inmon2005}, stores subject oriented, integrated data using a normalized approach. \textcite{Kimball2013} take a bottom up path with dimensional modeling: star schemas of fact and dimension tables. Both approaches assume structured, stable sources. Security tool output is neither.

The data lake~\cite{Miloslavskaya2016} stores raw data in its native format, deferring schema to consumption time (schema on read). This accommodates format diversity but risks ``data swamps'' without governance~\cite{DAMA2017}.

The lakehouse~\cite{Armbrust2021} combines data lake flexibility with warehouse governance through open table formats adding \gls{acid} transactions, schema enforcement, and time travel on top of lake storage~\cite{Lee2024, Thalpati2024}. It accepts semi structured tool output and gives the governance and fast queries needed for both dashboards and operational lookups.

The medallion architecture~\cite{Strengholt2025} organizes lakehouse data into three layers:
\begin{itemize}
    \item \textbf{Bronze}: Raw data with minimal transformation, preserving original source schemas.
    \item \textbf{Silver}: Cleaned, validated, and normalized data conforming to a unified schema.
    \item \textbf{Gold}: aggregated metrics and enriched datasets ready for queries.
\end{itemize}
This maps naturally to security data integration. Bronze captures raw tool output in source native schemas, silver normalizes findings into a vendor agnostic model, and gold computes aggregated risk metrics and enriched datasets stakeholders consume.

A security data platform must serve two access patterns. \Gls{olap} queries power dashboards and trend analysis over large aggregated datasets. \Gls{oltp} access supports operational workflows such as issue tracker integration and real time risk lookups, where low latency reads and writes to individual records are essential. Both inform the serving architecture in \autoref{ch:framework}.

%%% 1.5.2 %%%

\subsection{Data Integration Patterns}
\label{sec:data-integration-patterns}

\textcite{Reis2022} distinguish \gls{etl} from \gls{elt}. \Gls{etl} transforms data before loading, requiring upfront schema knowledge. \Gls{elt} loads raw data first and transforms in place, aligning with lakehouse architectures where distributed compute engines perform transformations at scale~\cite{Thalpati2024}. Security tool output varies and evolves, so upfront transformation breaks. \Gls{elt} fits.

Full reingestion does not scale across thousands of repositories and dozens of tools. Incremental ingestion pulls only new or changed records. The high water mark pattern tracks a timestamp or cursor per source. \Gls{cdc} captures changes at the source level, propagating inserts, updates, and deletes as events~\cite{Reis2022}.

Source \glspl{api} and formats change regularly, so rigid schemas break pipelines on every upstream change. Schema on read stores raw data in its original structure and applies schema at query time. Additive evolution accepts new fields~\cite{Lee2024}, and existing queries keep working.

Reruns are idempotent so retries and replays do not duplicate. Each layer validates: schema at ingest, value ranges at normalization, referential integrity at aggregation. Records that fail validation go to quarantine tables~\cite{DAMA2017}.

%%% 1.5.3 %%%

\subsection{Domain Data Model}
\label{sec:data-entities}

The security domains analyzed above produce data about a common set of entities and relationships. A vendor agnostic conceptual model must precede physical schemas. The domain model has five primary entities:
\begin{itemize}
    \item \textbf{Applications} carry business context from asset inventories (\autoref{sec:app-inventory}): name, owning team, criticality tier, lifecycle status, and compliance scope. An application represents a business level unit that may span multiple repositories and deployment environments.
    \item \textbf{Repositories} represent technical assets from \gls{scm} platforms (\autoref{sec:sw-dev-analysis}): code location, primary language, visibility, activity indicators, and archive status. The repository is the primary unit around which security findings are grouped.
    \item \textbf{Findings} capture security issues from any tool category analyzed in \autoref{sec:static-appsec} and \autoref{sec:dynamic-appsec}: severity, status, source tool, detection timestamp, affected code location, and rule or check identifier. Each finding traces to a specific tool scan.
    \item \textbf{Vulnerabilities} are \gls{cve} identified issues enriched with three signals: \gls{cvss} severity from the \gls{nvd}, exploitation probability from \gls{epss}, and confirmed exploitation status from \gls{cisa} \gls{kev}. Multiple findings from different tools may reference the same vulnerability.
    \item \textbf{Teams} provide organizational ownership, linking personnel to applications and remediation responsibilities. Team structure enables filtering and aggregation by organizational unit.
\end{itemize}

More entities add development and supply chain context:
\begin{itemize}
    \item \textbf{Commits} record individual code changes with author, timestamp, and affected files. They link findings to specific code versions and establish authorship for attribution.
    \item \textbf{Pull requests} represent code change proposals where security scans typically execute. Scan results are often reported per pull request, making it a natural grouping unit for new findings.
    \item \textbf{Pipeline runs} capture \gls{cicd} execution records: which security tools ran, when, against which commit, and whether security gates passed. They indicate scan coverage and tool health across repositories.
    \item \textbf{Issues} track remediation work items in systems such as Jira. Linking findings to issues enables \gls{mttr} calculation and \gls{sla} compliance monitoring.
    \item \textbf{Dependencies} represent third party libraries identified through \gls{sca}: package name, version, license, and associated \gls{cve} identifiers. They connect \gls{sca} findings to the specific library version that introduced the vulnerability.
    \item \textbf{Branch protection policies} capture governance configurations from \gls{scm} platforms: required reviewers, mandatory status checks, and merge restrictions. They serve as indicators of development process maturity and security hygiene at the repository level.
\end{itemize}

The mapping from app to repo is the key relationship. It links findings to business context and is many to many: shared libraries serve multiple applications, and microservice applications span multiple repositories. Teams own applications, establishing the chain from organizational accountability through business applications to technical assets and findings. Dependencies bridge repositories and vulnerabilities: an \gls{sca} finding links a specific library version to a known \gls{cve}. Issues track remediation.

The structure maps to dimensional modeling~\cite{Kimball2013}. Findings are facts. Applications, repositories, and teams are dimensions. Commits, pull requests, and pipeline runs add temporal and process dimensions. Cross tool deduplication collapses related findings while preserving traceability to each source.

Stakeholders consume this data through different patterns:
\begin{itemize}
    \item Application owners need aggregated risk dashboards showing finding counts by severity, remediation progress, and compliance status.
    \item Developers need actionable findings with code level context, delivered through issue trackers.
    \item Security experts need drill down access to raw findings, audit trails, and cross tool correlation for triage.
    \item Leadership needs executive metrics: \gls{mttr}, \gls{sla} compliance, vulnerability density trends, and portfolio level comparisons.
\end{itemize}
These span the \gls{olap} and \gls{oltp} requirements from \autoref{sec:data-architecture} and drive the serving architecture in \autoref{ch:framework}.

\section{Related Work and Gap Analysis}
\label{sec:related-work}

No standard approach exists for consolidating security tool output into a unified data platform. Organizations face a fragmented landscape of partial solutions.

%%% 1.6.1 %%%

\subsection{Existing Approaches}

\textcite{Gartner2023ASPM} define \gls{aspm} as tools that continuously manage application risk through collection, analysis, and prioritization of security issues across the software lifecycle. Commercial platforms such as Apiiro, Cycode, ArmorCode, and Snyk AppRisk aggregate findings into unified dashboards with correlation and risk scoring, but they are proprietary. Pipelines cannot be customized, custom \gls{ml} cannot be added, and integrations are limited to what the vendor supports.

Platform native features cover only their own ecosystem. GitHub Advanced Security provides code scanning via CodeQL, secret scanning, and dependency review~\cite{GitHubGHAS2025}. GitLab bundles \gls{sast}, \gls{dast}, dependency scanning, container scanning, and a security dashboard~\cite{GitLabSecurity2025}. Organizations using multiple \gls{scm} platforms or third party tools cannot consolidate through them.

DefectDojo~\cite{DefectDojo2024} is the most prominent open source alternative, supporting imports from over 150 tools through format specific parsers. It was designed as a vulnerability management interface rather than a data platform. Its PostgreSQL backend limits enterprise scale analytics, and advanced \gls{api} connectors are commercial only. \Gls{ocsf}~\cite{OCSF2024} standardizes security event schemas for \gls{siem} and \gls{soar} but does not model application level entities such as repositories, applications, or teams.

Many enterprises build ad hoc integrations: custom scripts, \gls{etl} pipelines, and dashboards from manual exports. These lack schema governance, break on \gls{api} changes, and persist as institutional knowledge in unmaintained scripts.

%%% 1.6.2 %%%

\subsection{Databricks Lakewatch}
\label{sec:lakewatch}

Databricks announced Lakewatch in March 2026 as an open, agentic \gls{siem} built on the Databricks lakehouse~\cite{Databricks2026Lakewatch}. It unifies security, \gls{it}, and business data in a single governed environment powered by Delta Lake and Unity Catalog, with agentic triage, Detection as Code, and integrations from Wiz, Palo Alto Networks, Okta, and Zscaler.

Lakewatch focuses on runtime security operations: threat detection, incident response, alert triage, and log analytics. This framework focuses on application security posture: findings from \gls{sast}, \gls{sca}, \gls{dast}, secret scanning, container scanning, and \gls{iac} tools, combined with remediation tracking and risk aggregation. The two are complementary. Shared lakehouse infrastructure enables data exchange: Lakewatch could consume application risk scores for incident triage, and the framework could ingest Lakewatch's runtime detections as a finding source.

\section{Selected Sources}
\label{sec:selected-sources}

The reference implementation in \autoref{ch:implementation} instantiates the framework against nine source systems chosen to cover the ingestion and integration patterns that the framework must support, while keeping the sample tractable. The selection spans all three detection tiers: static testing, dynamic testing, and runtime security.

\subsection{Selection Criteria}

The nine sources are selected based on five criteria:

\begin{enumerate}
    \item \textbf{Open source or free tier available.} The reference implementation must be reproducible without commercial licenses.
    \item \textbf{Full domain coverage across three detection tiers.} The nine together must cover every domain in the framework: \gls{cmdb}, \gls{scm}, and the three detection tiers, namely static testing (\gls{sast}, \gls{sca}, secrets), dynamic testing (\gls{dast}), and runtime security (\gls{waf}).
    \item \textbf{\Gls{api} heterogeneity.} The selection deliberately includes \gls{rest} (ServiceNow, SonarQube, Dependency-Track, GitHub, GitLab, OWASP ZAP, AWS WAF), GraphQL (GitHub, GitLab), and \gls{cli} wrapped (Semgrep, TruffleHog) sources so the connector contract is exercised across integration styles.
    \item \textbf{Limit heterogeneity to nine to maintain scope control.} The nine sources cover the ingestion and integration patterns that the framework must support. A wider sample would dilute pattern coverage without strengthening the framework claim.
    \item \textbf{Industry adoption.} Each tool is in widespread enterprise use.
\end{enumerate}

\subsection{Selected Sources}

\begin{itemize}
    \item \textbf{ServiceNow}: \gls{cmdb}. Dominant enterprise \gls{cmdb} with a free developer instance, \gls{rest} Table and CMDB Instance \glspl{api}, and native \inlinecode{sys\_updated\_on} high water mark.
    \item \textbf{GitHub}: \gls{scm} plus \gls{sast}, \gls{sca}, and secrets scanning integrated into the platform. \Gls{rest} and GraphQL \glspl{api}, rich webhook coverage, cursor pagination.
    \item \textbf{GitLab}: \gls{scm} plus security integrated into the platform. \Gls{rest} and GraphQL \glspl{api}, keyset and offset pagination, webhook coverage. Security findings require Ultimate tier or pipeline artifacts.
    \item \textbf{SonarQube}: \gls{sast} (static testing). Mature server product with a \gls{rest} Web \gls{api}, well documented severity scale, \inlinecode{updateDate} high water mark, and a scan completion webhook that complements scheduled polling.
    \item \textbf{Semgrep}: \gls{sast} (static testing). Modern engine with both a \gls{cli} deployment (\gls{cicd} embedded) and a hosted Cloud Platform \gls{api}. Exercises the dual \gls{cli} artifact and server \gls{api} ingestion pattern.
    \item \textbf{Dependency-Track}: \gls{sca} (static testing). \gls{owasp} project with a \gls{rest} \gls{api}, \gls{sbom} centric (CycloneDX, SPDX) vulnerability correlation across multiple advisory sources.
    \item \textbf{TruffleHog}: secrets (static testing). \Gls{cli} tool with no server \gls{api}, distinguished by live credential verification that populates the canonical \inlinecode{validity\_status} field.
    \item \textbf{OWASP ZAP}: \gls{dast} (dynamic testing). Open source dynamic scanner operated as a long running daemon with a \gls{rest} \gls{api}~\parencite{OWASPZAP2024} for scan orchestration and alert retrieval. \Gls{url} based findings represent the dynamic testing tier and exercise the on demand scan lifecycle integration pattern.
    \item \textbf{AWS WAF}: \gls{waf} (runtime security). Managed web application firewall exposing matched request samples through the \inlinecode{GetSampledRequests} \gls{api}~\parencite{AWSWAF2026}, with full event logs available via CloudWatch. Event based findings linked to workloads by \gls{arn} and tag represent the runtime security tier and exercise the time window sampled retrieval pattern.
\end{itemize}

\subsection{Cross Source Synthesis}
\label{sec:cross-source-synthesis}

Across the nine sources, four patterns recur: ticket like, resource like, finding like, and event like. Severity scales span three to six levels with overlapping but not identical vocabularies. Status vocabularies diverge more sharply, with scanner specific states that rarely map one to one with a common lifecycle. Five pagination strategies appear: offset (ServiceNow, SonarQube, Dependency-Track), cursor (GitHub \gls{rest}, Semgrep Cloud), GraphQL cursor (GitHub and GitLab GraphQL), keyset (GitLab \gls{rest}), and none (\gls{cli} based sources, AWS WAF sampled requests). The sources also split on an \textbf{operational pattern} axis. Periodic global scanners (SonarQube, Dependency-Track, Semgrep Cloud) are polled via \inlinecode{updated\_at} cursors. \gls{cicd} step scanners (Semgrep Docker, TruffleHog) run per commit and are indexed by commit \gls{sha}. On demand dynamic scanners (OWASP ZAP) are read via the scan lifecycle \gls{api}. Runtime telemetry sources (AWS WAF) are sampled over time windows. Together these exercise all five ingestion strategies the framework prescribes.

The \href{https://vkraus.github.io/appsec-mvp/platform/reference/source-capability-matrix/}{source capability matrix reference page} tabulates the nine sources against the capabilities that matter for connector design. This matrix drives the derivations in \autoref{sec:data-model}: the Silver Entity and Silver Finding patterns must accommodate sources varying across every column, and the connector framework rules in \autoref{sec:connector-framework} must commit to defaults that work uniformly.

This thesis fills the gap with a vendor agnostic framework for application security data. It applies lakehouse architecture and the medallion pattern to ingest tool output, normalize it into a domain model, and serve it through \gls{olap} and \gls{oltp} interfaces. A new source needs only a connector module. \autoref{ch:framework} presents the framework, and \autoref{ch:implementation} demonstrates its implementation.

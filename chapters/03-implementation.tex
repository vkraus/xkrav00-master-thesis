\chapter{MVP Implementation}
\label{ch:implementation}

The reference implementation instantiates the framework from the \hyperref[ch:framework]{Framework} chapter as a Declarative Automation Bundle, formerly Databricks Asset Bundle~\parencite{DatabricksDAB2026}. It covers the three connector categories plus the artifact ingestion pattern across the nine sources selected in the \hyperref[sec:selected-sources]{Selected Sources section}: two \gls{scm} platforms, four scanners across static and dynamic testing, a \gls{cmdb}, a secrets tool, and a runtime security source. It is a minimum viable product. Open items are listed in the \hyperref[sec:impl-results]{Aggregate Results section}.

The contribution is twofold. The contract of three categories holds across all nine sources, and the resulting code fits one small repeating module layout. The chain of four skills was run across the nine source specifications and produced the connector modules, runtime artifacts, bundle fragments, tests, and documentation evidence, with reviewer subagent cycles catching named defect classes (\hyperref[sec:iteration-summary]{Iteration Summary section}, \hyperref[sec:ai-eval]{Evaluation of AI Instantiability section}). The implementation evidence is not identical for every source: some sources were exercised against live systems, some are backed only by fixtures, some Spark wrappers write Silver frames with rows, and some contract wrappers still return empty Silver frames while mapping helpers at row level are tested. The \hyperref[sec:impl-results]{Aggregate Results section} states those boundaries. The \hyperref[sec:impl-representative-connectors]{Representative Connectors section} shows one concrete example from each implemented ingestion type: ServiceNow on Lakeflow Connect, GitHub on PyGitHub~\parencite{PyGithubDocs2025}, SonarQube through \gls{dltool}, and \gls{owasp} \gls{zap} through the artifact path.

\section{Methodology}
\label{sec:impl-methodology}

The implementation follows the procedure below for every source in the \hyperref[sec:selected-sources]{Selected Sources section}:

\begin{enumerate}
    \item \textbf{Resolve the ingestion category.} The source is matched against the three categories defined in the \hyperref[sec:connector-abstraction]{Connector Abstraction section}. The evaluation order is fixed: Lakeflow Connect~\parencite{DatabricksLakeflowConnect2025} first, then a maintained Python \gls{sdk}, then \gls{dltool}. Tools that only ship a \gls{cli} fall outside the axis of three categories and follow the artifact pattern at the \gls{cicd} step described in the \hyperref[sec:ingestion-patterns]{Ingestion Patterns section}. The \hyperref[sec:ingestion-category-assignment]{Ingestion Category Assignment section} carries out this step for all nine sources.
    \item \textbf{Instantiate the module layout for the connector.} Every connector carries the same files under \inlinecode{src/connectors/<source>/}: \inlinecode{ingest.py}, \inlinecode{transform.py}, \inlinecode{mapping.yml}, \inlinecode{config.yml}, \inlinecode{severity.yml}, and \inlinecode{status.yml}. Bundle resources, tests, and the secret loading script are colocated with the connector code. For Lakeflow Connect sources, \inlinecode{ingest.py} is reduced to a module docstring and ingestion is declared in the bundle fragment as a \inlinecode{pipelines} resource with an \inlinecode{ingestion\_definition}.
    \item \textbf{Use the mapping artifact as the transformation specification.} The \inlinecode{mapping.yml} file for the connector records the intended column derivation from bronze to silver given by the \href{https://vkraus.github.io/appsec-mvp/platform/reference/canonical-mapping/}{published mapping requirements}. Severity and status lookups live in the connector folder as \inlinecode{severity.yml} and \inlinecode{status.yml}. \inlinecode{src/platform/silver.py} provides severity rank and status bucket normalization helpers and deduplication utilities shared across connectors. The current \gls{mvp} keeps the mapping as the authoritative artifact but applies it through Python helpers and Spark code for each source rather than through a generic YAML applicator. Several connectors have tested helpers at row level while their Spark contract wrapper still returns an empty frame with the target schema. The corresponding backlog item appears in the \hyperref[sec:future-work]{Future Work section}.
    \item \textbf{Test in the layered strategy from the \hyperref[sec:connector-testing]{Connector Testing and Validation section}.} Tests divide along the signature of the code they exercise. Row level logic in pure Python (parser logic, mapping application, \gls{hwm} state, dedup key construction) runs locally against \inlinecode{list[dict]} fixtures with no \inlinecode{SparkSession}. DataFrame logic (transformations, envelope stamping, schema enforcement) runs through a session scoped Databricks Connect fixture that attaches to a remote workspace, so the test runtime matches the production runtime. Tests live under \inlinecode{src/connectors/<source>/tests/} and are linked to requirement IDs through \inlinecode{@pytest.mark.requirement} markers.
    \item \textbf{Run the skill chain pass for the source.} The Claude Code skill chain (analyze-source, provision-source, generate-connector, validate-implementation) executes against the source and writes evidence rows to the documentation site: an Implementation log entry per pass and a Validation table keyed by requirement IDs. Each skill pass is then reviewed by a separate subagent (one for spec compliance, one for code quality), whose findings are folded back as follow up commits before the next source moves forward. The \hyperref[sec:iteration-summary]{Iteration Summary section} records the defect classes the reviewer cycle caught.
\end{enumerate}

The procedure is repeatable because the source category is resolved before generation and the connector folder layout stays fixed across categories. A generator that emits the layout for a new source only needs to vary \inlinecode{ingest.py} and the bundle resource kind. The \href{https://vkraus.github.io/appsec-mvp/}{documentation site} makes the run auditable by recording the Implementation log and Validation table for each source.

In this thesis, \gls{ai} instantiable means prompt based generation through tailored agent skills created for the framework. The skills encode the connector procedure, required artifacts, and validation steps. The framework user supplies missing environment facts, reviews generated changes, and reruns the skill chain until requirement linked tests and reviewer checks pass.

\section{Project Structure}
\label{sec:impl-project-structure}

The reference implementation is distributed across two repositories that separate the thesis document from the \gls{mvp} code.

\begin{itemize}
    \item The thesis repository holds the \LaTeX{} sources for this document.
    \item The \gls{mvp} implementation repository holds the reference implementation described in the remainder of this section. The source for the documentation site lives inside the same repository under \inlinecode{mkdocs/}. The \href{https://vkraus.github.io/appsec-mvp/}{published site} is the framework user reference and the trail of evidence for each connector.
\end{itemize}

\subsection{Layering rule}
\label{sec:impl-layering-rule}

The repository is organized into three install layers with no upward or sideways dependencies in setup code: platform, then connectors, then analytics. The platform layer must not pre-declare resources for any specific connector. No source schemas, volumes, connections, or secrets live in \inlinecode{src/platform/resources/}. Each connector owns its own bronze and silver schemas, secret loading script, and bundle resources. The analytics layer reads only the connector agnostic silver tables (\inlinecode{silver.findings}, \inlinecode{silver.repositories}, \inlinecode{silver.applications}, \inlinecode{silver.app\_repo\_mapping}, \inlinecode{silver.hwm}, and \inlinecode{silver.suppression\_rules}). The one ordering constraint is data level, not setup code level. An \gls{scm} connector (GitHub or GitLab) must run first at job time because non \gls{scm} connectors map findings onto repository entities populated by \gls{scm}. The bundle deploys all declared resources regardless of install order.

There are no top level \inlinecode{tests/}, \inlinecode{config/}, \inlinecode{resources/}, \inlinecode{sql/}, or \inlinecode{infra/terraform/} directories. \autoref{lst:mvp-tree} shows the realized layout with two connector examples expanded.

\section{Ingestion Category Assignment}
\label{sec:ingestion-category-assignment}

Each source is resolved to one of the three ingestion categories defined in the \hyperref[sec:connector-abstraction]{Connector Abstraction section} before its connector module is written. The evaluation order is Lakeflow Connect, then \gls{sdk}, then \gls{dltool}. \Gls{cli} only tools fall outside the three categories and follow the \gls{cicd} step artifact pattern (\hyperref[sec:ingestion-patterns]{Ingestion Patterns section}). The full per source functional requirements live on the documentation site. The reference links below cite the deciding factor only.

\begin{itemize}
    \item \textbf{ServiceNow}: Lakeflow Connect. Supported natively by the platform~\href{https://vkraus.github.io/appsec-mvp/connectors/cmdb/servicenow/}{(source reference)}, so \inlinecode{ingest.py} carries only the contract wrapper and the bundle fragment declares the pipeline.

    \item \textbf{GitHub}: \gls{sdk} via PyGitHub. Lakeflow Connect does not support it at \gls{mvp} time, and PyGitHub covers the required endpoints, handles \inlinecode{Link} header pagination, and exposes rate limit status~\href{https://vkraus.github.io/appsec-mvp/connectors/scm/github/}{(source reference)}.

    \item \textbf{GitLab}: \gls{sdk} via python-gitlab~\parencite{PythonGitlabDocs2025}. No Lakeflow Connect support, and the official client handles keyset pagination transparently~\href{https://vkraus.github.io/appsec-mvp/connectors/scm/gitlab/}{(source reference)}.

    \item \textbf{SonarQube}~\parencite{SonarQube2024}: \gls{dltool}. No first party Python \gls{sdk}, and the \inlinecode{rest\_api} source template that ships with \gls{dltool} covers all requirements declaratively against the Web \gls{api}~\href{https://vkraus.github.io/appsec-mvp/connectors/sast/sonarqube/}{(source reference)}.

    \item \textbf{Semgrep}: artifact path. The free \gls{cli} writes a \gls{json} report per commit from a \gls{cicd} step, and \inlinecode{ingest.py} reads from \inlinecode{periodic/semgrep/} and \inlinecode{cicd/semgrep/} prefixes~\href{https://vkraus.github.io/appsec-mvp/connectors/sast/semgrep/}{(source reference)}.

    \item \textbf{Dependency-Track}~\parencite{DependencyTrack2024}: \gls{dltool}. No first party Python \gls{sdk}, and the published OpenAPI document configures \gls{dltool} directly~\href{https://vkraus.github.io/appsec-mvp/connectors/sca/dependency-track/}{(source reference)}.

    \item \textbf{TruffleHog}~\parencite{TruffleHog2024}: artifact path. \Gls{cli} tool with no server \gls{api}, same pattern as Semgrep~\href{https://vkraus.github.io/appsec-mvp/connectors/secrets/trufflehog/}{(source reference)}.

    \item \textbf{\gls{owasp} \gls{zap}}: artifact path. \inlinecode{ingest.py} supports two trigger contexts (on demand against the daemon, and reads of \gls{cicd} step artifacts) and dispatches both into the same bronze table~\href{https://vkraus.github.io/appsec-mvp/connectors/dast/owasp-zap/}{(source reference)}.

    \item \textbf{\gls{aws} \gls{waf}}: \gls{sdk} via boto3~\parencite{Boto32025}. The connector ships two ingestion modes selected by \inlinecode{config.yml::ingestion\_mode}. The preferred mode reads full request logs delivered by Kinesis Data Firehose to an S3 prefix through an autoloader read. The fallback mode calls \inlinecode{boto3.client("wafv2").get\_sampled\_requests} with \gls{iam} signed credentials and preserves the per record \inlinecode{Weight} field~\href{https://vkraus.github.io/appsec-mvp/connectors/waf/aws-waf/}{(source reference)}.
\end{itemize}

\section{Representative Connectors}
\label{sec:impl-representative-connectors}

Four connectors show the implementation range. ServiceNow represents the Lakeflow Connect case, where \inlinecode{ingest.py} reduces to a thin contract wrapper and the bundle fragment carries the ingestion specification. GitHub represents the \gls{sdk} case, where \inlinecode{ingest.py} composes client calls into iterators over bronze records. SonarQube represents the \gls{dltool} case, where tested Python helpers cover authentication, pagination, rate limits, and high water marks while the Spark transform writes \inlinecode{silver.findings} rows. \Gls{owasp} \gls{zap} represents the artifact path, where a \gls{cicd} report or daemon scan lands in bronze and a Spark transform explodes alerts into URL based findings.

\subsection{ServiceNow: Lakeflow Connect Pipeline}
\label{sec:impl-servicenow-connector}

The ServiceNow connector performs no live Python ingestion. The \inlinecode{ingest.py} module carries a module docstring pointing at the bundle fragment under \inlinecode{src/connectors/servicenow/}\allowbreak\inlinecode{resources/pipeline.yml} (reproduced in \autoref{lst:servicenow-pipeline}) and a thin framework contract wrapper (\inlinecode{ingest\_contract}) that validates the credential set so a misconfigured bundle job fails fast. Lakeflow Connect performs the actual \gls{http} ingestion against ServiceNow. Authentication is carried by a Databricks Connection declared in the same folder under \inlinecode{resources/connection.yml} and referenced by name. The \inlinecode{objects} block enumerates the two \gls{cmdb} tables the silver layer consumes and their destination tables in bronze. The \inlinecode{cmdb\_ci\_business\_app} table supplies application records, and \inlinecode{cmdb\_rel\_ci} supplies the relationship edges used by the \gls{mvp} app repository mapping path. Fuller production inventories would add explicit repository link fields or additional relationship classes. Schedule and target catalog come from bundle variables so the same fragment can promote across dev, staging, and prod.

\begin{lstlisting}[language=yaml,caption={[ServiceNow pipeline bundle fragment]\texttt{src/connectors/servicenow/resources/pipeline.yml}},label={lst:servicenow-pipeline}]
resources:
  pipelines:
    servicenow_ingest:
      name: servicenow_ingest
      catalog: ${var.catalog}
      target: bronze_servicenow
      continuous: false
      schedule:
        quartz_cron_expression: "0 0 * * * ?"
        timezone_id: UTC
      ingestion_definition:
        connection_name: servicenow
        objects:
          - table:
              source_schema: default
              source_table: cmdb_ci_business_app
              destination_catalog: ${var.catalog}
              destination_schema: bronze_servicenow
              destination_table: business_applications
          - table:
              source_schema: default
              source_table: cmdb_rel_ci
              destination_catalog: ${var.catalog}
              destination_schema: bronze_servicenow
              destination_table: app_cis
\end{lstlisting}

The framework prescribed connector layout is preserved. \inlinecode{mapping.yml}, \inlinecode{config.yml}, \inlinecode{severity.yml}, \inlinecode{status.yml}, and \inlinecode{transform.py} continue to govern the transformation from bronze to silver. Only \inlinecode{ingest.py} changes form, from a Python module to a declaration embedded in the bundle. That is the trade the Lakeflow Connect category offers: no pagination, authentication, or retry code written by hand, in exchange for binding the connector to a platform maintained capability.

\subsection{GitHub: PyGitHub SDK Module}
\label{sec:impl-github-connector}

The GitHub connector uses PyGitHub. The \inlinecode{ingest.py} module exposes three names: a \inlinecode{build\_github\_client} factory, an \inlinecode{ingest\_contract} framework wrapper that demonstrates the documented traversal, and a \inlinecode{verify\_webhook\_signature} HMAC helper that handles webhook receipt outside SDK territory. The traversal calls \inlinecode{client.get\_organization(org).get\_repos()} and receives a \inlinecode{PaginatedList} of \inlinecode{Repository} instances. Each repository then exposes \inlinecode{repo.get\_pulls(state, since=hwm\_value)} and \inlinecode{repo.get\_codescan\_alerts()} for walking the finding streams. \autoref{lst:github-ingest} reproduces the client factory as the representative fragment.

\begin{lstlisting}[language=Python,caption={[GitHub connector client factory]\texttt{src/connectors/github/ingest.py} (client factory shown)},label={lst:github-ingest}]
from github import Auth, Github, GithubRetry


def build_github_client(token: str) -> Github:
    """Authenticated Github client with retry tuned for
    secondary rate limits."""
    auth = Auth.Token(token)
    retry = GithubRetry(
        total=10, backoff_factor=2.0, secondary_rate_wait=60
    )
    return Github(auth=auth, retry=retry, per_page=100)
\end{lstlisting}

PyGitHub absorbs the cross cutting concerns of authentication, pagination, and retry. \inlinecode{GithubRetry}, a \inlinecode{urllib3.Retry} subclass shipped with the library, recognizes the secondary GitHub rate limit signal that arrives as \gls{http}~403 with a \inlinecode{Retry-After} header. A plain \inlinecode{Retry(status\_forcelist=[429, 5xx])} does not cover that path. The incremental state contract from the framework (REQ-ING-HWM) maps onto a built in PyGitHub mechanism: resource accessors such as \inlinecode{Repository.get\_pulls(state="closed", since=hwm\_value)} accept a \inlinecode{since} parameter, so high water mark filtering pushes down to the \gls{api} call instead of running client side. The page size is set to the documented PyGitHub maximum of 100 to minimize round trips.

The tests under \inlinecode{src/connectors/github/tests/} fake PyGitHub at the object graph level rather than at the \gls{http} level. A test fixture builds \inlinecode{MagicMock} instances modeled on the PyGitHub \inlinecode{Github}, \inlinecode{Organization}, \inlinecode{Repository}, and \inlinecode{PaginatedList} classes, each exposing the attributes the production code calls. The contract under test is the composition of \gls{sdk} calls in the connector, not the \gls{http} behavior of the library.

\subsection{SonarQube: dltool REST Module}
\label{sec:impl-sonarqube-connector}

The SonarQube connector represents the \gls{dltool} path. SonarQube exposes a paginated \gls{rest} Web \gls{api} rather than a maintained Python \gls{sdk}, and Lakeflow Connect has no native SonarQube source in the \gls{mvp} environment. The \inlinecode{ingest.py} module therefore keeps the connector contract in Python and delegates the source traversal to the \inlinecode{rest\_api} source pattern. The public helpers make the contract testable without a live server: \inlinecode{resolve\_token} binds REQ-ING-AUTH to the platform secret scope, \inlinecode{iter\_issue\_pages} follows the \inlinecode{p}/\inlinecode{ps} pagination model shown in \autoref{lst:sonarqube-ingest}, \inlinecode{call\_with\_backoff} implements retry on rate limit responses, and \inlinecode{advance\_hwm} advances the native \inlinecode{updateDate} high water mark.

\begin{lstlisting}[language=Python,caption={[SonarQube issue page iterator]\texttt{src/connectors/sonarqube/ingest.py} (excerpt)},label={lst:sonarqube-ingest}]
def iter_issue_pages(fetch_page, *, page_size: int = 500):
    first = fetch_page(1, page_size)
    total = int(first.get("paging", {}).get("total", 0))
    issues = first.get("issues") or []
    yield issues

    if total <= page_size:
        return
    if total > 10_000:
        raise RuntimeError(
            "sonarqube: issue search exceeds the 10,000 row cap"
        )

    pages_remaining = -(-total // page_size) - 1
    for idx in range(2, 2 + pages_remaining):
        page = fetch_page(idx, page_size)
        yield page.get("issues") or []
\end{lstlisting}

The transform is more complete than the other \gls{dltool} source in the sample. \inlinecode{transform.py} parses bronze issue payloads, filters SonarQube \inlinecode{CODE\_SMELL} records out of the security findings stream, splits the \inlinecode{component} value into repository and file path, normalizes severity and status through colocated lookup files, and emits rows with the \inlinecode{silver.findings} schema. This makes SonarQube the clearest \gls{dltool} example: it shows the hand written boundary code that remains around a generated \gls{rest} source, and it also demonstrates a Spark transform that writes Silver findings.

\subsection{OWASP ZAP: Artifact and Daemon Path}
\label{sec:impl-zap-connector}

The \gls{owasp} \gls{zap} connector represents the artifact path. The common path is a \gls{json} report produced by \inlinecode{zap-baseline.py}, \inlinecode{zap-full-scan.py}, or \inlinecode{zap-api-scan.py} in a \gls{cicd} step and written under the configured \inlinecode{cicd/zap/} prefix. The same module also supports an on demand daemon path against the ZAP \gls{rest} \gls{api}. \inlinecode{classify\_trigger} separates the two trigger contexts, \inlinecode{iter\_paged\_alerts} handles offset pagination for daemon alerts, and \inlinecode{ingest\_contract} routes the configured path into the bronze table. \autoref{lst:zap-ingest} shows the two ingestion decisions that are specific to ZAP: routing an input to an artifact or daemon trigger context, and reading daemon alerts until the endpoint returns a short page.

\begin{lstlisting}[language=Python,caption={[OWASP ZAP trigger routing and alert paging]\texttt{src/connectors/owasp\_zap/ingest.py} (excerpt)},label={lst:zap-ingest}]
def classify_trigger(path_or_url: str) -> str:
    object_storage_schemes = ("s3://", "s3a://", "abfss://", "gs://")
    if path_or_url.startswith(object_storage_schemes):
        if "/cicd/zap/" in path_or_url:
            return "cicd"
    if path_or_url.startswith(("http://", "https://")):
        return "on_demand"
    raise ValueError(f"cannot route ZAP source {path_or_url!r}")


def iter_paged_alerts(fetch_json, base_url, *, baseurl, apikey):
    start = 0
    page_size = 5000
    while True:
        url = build_alerts_url(
            base_url, baseurl=baseurl, apikey=apikey,
            start=start, count=page_size
        )
        alerts = (fetch_json(url) or {}).get("alerts") or []
        if not alerts:
            return
        yield from alerts
        if len(alerts) < page_size:
            return
        start += page_size
\end{lstlisting}

The ZAP transform illustrates why artifact ingestion is still part of the framework even though it sits outside the three source category order. The bronze payload is a nested scan report with \inlinecode{site}, \inlinecode{alerts}, and \inlinecode{instances} arrays. \inlinecode{transform.py} explodes that structure to one Silver row per alert instance, maps the ZAP risk vocabulary to the standard severity model, normalizes missing \gls{cwe} placeholders to null, and stores the affected \gls{url} instead of file and line coordinates. The output is a URL based \gls{dast} finding that can later be joined to deployment and application context.

\section{Discussion}
\label{sec:impl-discussion}

\subsection{Contract of three categories}

Every source in the sample resolved to one of the three connector categories or to the artifact ingestion pattern of the \hyperref[sec:ingestion-patterns]{Ingestion Patterns section}. No source required another connector category. The Lakeflow Connect and \gls{sdk} cases produce visibly different layouts: ServiceNow has no Python ingestion file of substance, while GitHub has a small flat \inlinecode{ingest.py} composed of \gls{sdk} calls. Both preserve the module layout prescribed by the framework, with platform lock in on one side and per source client knowledge on the other.

\subsection{Declarative mapping}

Connectors share severity and status normalization helpers in \inlinecode{src/platform/silver.py} and keep lookup tables as YAML alongside the connector code. The \inlinecode{mapping.yml} files document the intended derivation for every source. In the current \gls{mvp}, the mapping is applied by Python helpers and Spark code for each source rather than by a generic declarative applicator. SonarQube and \gls{owasp} \gls{zap} demonstrate Spark transforms that write rows to \inlinecode{silver.findings}. Several other connectors still expose Spark wrappers that return only the target schema while their mapping helpers at row level are tested. Aligning the \gls{mvp} with the declarative mapping prescription of the \hyperref[sec:transformation-patterns]{Transformation Patterns section} is recorded in the \hyperref[sec:future-work]{Future Work section}.

\subsection{Iteration Summary}
\label{sec:iteration-summary}

Review caught the iterations below. Each one is classified against the acceptance criterion in the \hyperref[sec:ai-eval]{Evaluation of AI Instantiability section}: \textbf{framework gap} (a specification extension would have prevented the issue and would generalize), \textbf{source specific issue} (not generalizable beyond one source), or \textbf{environment setup} (setup or infrastructure outside framework scope). Earlier iterations before the structural redesign exposed three framework gaps: a hand written shared \gls{http} primitive that introduced an unsanctioned fourth ingestion category, a missing boundary validator on incremental state inputs, and a misconfigured retry policy on the GitHub client. The redesign closed all three by enforcing the layering rule of the \hyperref[sec:impl-layering-rule]{Layering rule section} and by binding the connector contract to the colocated test suite. The findings below are from the reviewer cycle after the redesign.

\begin{itemize}
    \item \textbf{Layering boundary that the redesign closed.} The layout before the redesign mixed top level \inlinecode{tests/}, \inlinecode{config/}, \inlinecode{resources/}, \inlinecode{sql/}, and \inlinecode{infra/terraform/} folders, and the platform layer predeclared resources for specific connectors. This permitted exactly the failure mode that the unsanctioned fourth ingestion category had exposed. The redesign moved every component to its own folder, deleted the predeclared resources from the platform layer, and stated the layering rule explicitly. \textbf{Framework gap.} The framework now states three install layers with no upward or sideways setup code dependencies, and the data level \gls{scm} first ordering is recorded separately as a job time constraint.

    \item \textbf{Schema drift between \gls{sql} \gls{ddl} and PySpark types.} Splitting the \inlinecode{sql/} tree into per layer ownership exposed inconsistencies between the \gls{ddl} for the silver tables and the \inlinecode{StructType} definitions in \inlinecode{src/platform/schemas.py}. The reviewer flagged the drift, and the implementation now includes schema/DDL contract tests for the realized Silver subset. Connector side writers for \inlinecode{silver.repositories} remain partial, and \inlinecode{silver.app\_repo\_mapping} is populated by the platform name and application code linker rather than by every source side relationship path. \textbf{Framework gap.} The framework should hold a single source of truth for silver schemas. The consolidation is recorded in the \hyperref[sec:future-work]{Future Work section}.

    \item \textbf{Secret scope mismatch in the GitHub ingest entry.} The post deploy bootstrap script defines a secret scope named \inlinecode{mvp-connectors}. The GitHub ingest entry point read from a scope named \inlinecode{appsec}, a residue from an earlier prototype. The reviewer caught the mismatch during the bootstrap script review. \textbf{Environment setup.} The fix aligned the entry point with the documented scope name.

    \item \textbf{Worktree pollution.} Several review cycles caught files that the redesign deleted reappearing on disk and being staged for inadvertent reintroduction (likely an editor or antivirus recreating them). Reviewers caught the pattern before bad commits landed. \textbf{Environment setup.} The pattern is not attributable to the framework.

    \item \textbf{Cron schedule collision between GitHub and SonarQube.} The GitHub and SonarQube connector jobs were originally scheduled with overlapping quartz cron expressions, so both jobs would dispatch on the same minute mark and contend for the shared cluster. The reviewer flagged the collision and the SonarQube schedule was offset to a non aligned minute. \textbf{Source specific issue.} The correction is specific to two job schedules and does not generalize.

    \item \textbf{IRSA OIDC trust policy gaps.} Migrating each connector Terraform runtime under \inlinecode{src/connectors/<source>/runtime/} exposed incomplete trust policy details on the IAM Roles for Service Accounts (IRSA) bindings. The reviewer required full trust policy declarations and explicit framework user inputs for OIDC issuer URLs. \textbf{Environment setup.} The corrections concern \gls{aws} account setup and are documented per connector under the \inlinecode{runtime/README.md} file.
\end{itemize}

Two of the six findings after the redesign classify as framework gaps. Both name a specific consolidation the framework should hold (the layering rule, a single source of truth for silver schemas). Three classify as environment setup and one as a source specific issue. The reviewer cycle caught all six before the commits landed, which is the empirical evidence behind the claim that the skill chain plus reviewer pattern catches named defect classes. The \hyperref[sec:ai-eval]{Evaluation of AI Instantiability section} lifts these findings to a defended claim about where the framework holds and where it admits further specification.
